# Merge the open pull requests in four groups

> Generated by swarm planning session on 2026-10-05. The team tools were not available in this session, so the product, UX, and engineering review was done in one pass from the agreed grouping. Assumptions are in the decision log.

## Summary

Thirteen pull requests are open. Four of them can land on `main` without sharing files. Three plan-only pull requests can land after their base is changed to `main`. One code stack has to be rebased onto current `main` and merged in order, because it edits the preview workflow that just became label-only. Four pull requests stay closed or untouched: two duplicate work already on `main`, one plans a close that already happened, and one Vercel UI branch does not contain current `main`.

## Problem Statement

The open list mixes a current code change, documentation, stale plans, and a stack that would overwrite `.github/workflows/preview.yml`. Merging by GitHub’s default base, or merging the stack before a rebase, either lands nothing on `main` or puts the old push-deploy rule back.

The person merging needs one order, a reason to retarget some bases, and an explicit skip list.

## UX Design

The surface is GitHub’s pull request page. There is no Dyad screen.

### User Flow

1. Open the pull request named in the current phase.
2. If its base is not `main`, change the base to `main` and read the new diff before merging.
3. Merge with a merge commit. Do not squash a stack: [#30](https://github.com/Awannaphasch2016/dyad/pull/30) contains the commits from [#26](https://github.com/Awannaphasch2016/dyad/pull/26), and a squash hides that.
4. After the merge, look at `main`’s copy of `.github/workflows/preview.yml` before starting the next pull request.
5. Stop at the skip list. Do not press “Update branch” on 14, 15, 40, or 16 in this pass.

### Key States

- **Default**: the pull request’s base is the one in the table below, and its merge state is the one recorded on 2026-10-05.
- **Loading**: GitHub is recomputing mergeability after a base change or rebase.
- **Empty**: a retarget to `main` shows no unique commits. Stop and do not merge that pull request.
- **Error**: the merge is conflicting, or the preview workflow on the incoming branch deletes `preview-image-id.mjs` or restores a `branches:` list under `on.push`. Resolve in favor of the label rule, then merge.

## Technical Design

### Architecture

Each pull request is merged into `main` only after `main` is its base. Several open pull requests name an older branch as the base. Those bases are already ancestors of `main`, so merging into them does not move `main`.

[#30](https://github.com/Awannaphasch2016/dyad/pull/30)’s branch contains [#26](https://github.com/Awannaphasch2016/dyad/pull/26)’s branch. Rebase 26 onto `origin/main` first, then rebase 30 onto the rebased 26. Retarget 30’s base to `main` only after 26’s rebased commits are on `main`, or GitHub will show 30 as containing both diffs and the second merge will be empty or conflicting.

The preview rule to protect is the one on `main` at `e8b66417`:

- `.github/workflows/preview.yml` runs on `pull_request` label events, checks out `github.event.pull_request.head.sha`, and calls `scripts/gascity/preview-image-id.mjs`.
- `.github/workflows/preview-image.yml` is `workflow_dispatch` only. It has no `branches:` list.
- `deploy/preview/transition.mjs` skips a `preview` label added to an already closed pull request. Close and unlabel still destroy.
