# Factory Implementation writes a blueprint before any file

> Generated by swarm planning session on 2026-10-05

## Summary

Implementation is the only factory phase that writes code, and it is also the only phase that can hold an app blueprint. Today its prompt says to build the approved Discovery summary immediately, so the model calls `write_file` first. The blueprint gate rejects every file because this chat has no approved blueprint. The fix is one prefilled blueprint card on that Implementation chat, then the existing approval follow-up builds the page.

## Problem Statement

A person who approved Discovery (page name, one sentence, and page contents) and pressed Continue lands in Implementation with the composer already filled: "Build the one-page site from this approved Discovery summary." Sending that starts a build turn. New apps are created with `needsAppBlueprint` copied from `enableAppBlueprint`, which defaults to true. `write_file` then throws:

`App blueprint must be created and approved before running write_file. Call write_app_blueprint first to present the blueprint for approval.`

The same rejection repeats once per file. The model then asks for `planning_questionnaire`, which repeats the Discovery interview. Discovery cannot create the card: it is Ask mode, and `write_app_blueprint` is a build-mode tool. Delivery does not write files.

## Scope

### In Scope (MVP)

- On a factory Implementation chat that still needs a blueprint, treat the approved Discovery summary as the completed questionnaire. Do not call `planning_questionnaire`, including when that tool's consent is "never".
- The first Implementation turn calls `write_app_blueprint` and stops. It maps the Discovery page name to `app_name`, and the sentence plus contents to `user_prompt` and `design_direction`. It proposes a primary color and the visuals that page needs. It omits `template_id` and `theme_id` so the user's settings stay in place.
- Keep the existing gate. `write_file` stays rejected until this chat's blueprint is approved.
- The existing approval follow-up is the turn that writes the one-page site and ends with the Implementation summary.
- Change the Implementation system prompt so it matches that order.

### Out of Scope (Follow-up)

- Turning the blueprint off for factory apps. Discovery never collected color, design direction, or visuals, so skipping the card would hide those choices inside the first file write.
- Persisting the in-memory blueprint across a preview restart.
- Collapsing several `write_file` failures in one turn into a single notice.
- Generating images before the user can see the page. The card's visual prompts stay text until approval.
- Plan-mode handoff. Accepting a plan already clears `needsAppBlueprint` and must keep doing that.
- Asking Discovery about templates, stacks, or themes.

## User Stories

- As someone who approved Discovery, I get one prefilled blueprint card and approve the name, look, color, and visuals before any file is written.
- As that person, I am not asked the three Discovery questions again, and I am not asked to pick a stack.
- As someone who turned blueprint mode off, Implementation builds the summary on the first turn, with no card and no blueprint error.

## UX Design

### User Flow

1. Discovery asks for the page name, one sentence, and the sections. It does not ask about frameworks, templates, or stacks. The person approves the Discovery summary and presses Continue.
2. Implementation opens with the prefilled summary. Sending it starts the turn.
3. The agent writes one blueprint card from that summary and stops. The card shows the page name, a design direction inferred from the sentence and contents, a proposed hex color, and the planned visuals. Template and theme are the user's settings.
4. The person edits any field on the card, then approves it.
5. Approval applies the name, template, and theme, clears `needsAppBlueprint` on the app, and starts a new turn. That turn writes the one-page site. The preview is how they judge the page.
6. They press Continue when the Implementation summary looks right. Delivery stays read-only and never shows the card.

### Key States

- **Default:** Implementation's first turn ends on the blueprint card. No file cards yet.
- **Loading:** The card streams in, the same way it does on a non-factory chat.
- **Empty:** A Discovery summary missing one of the three fields is a broken handoff. The agent does not invent the missing answer and does not write files.
- **Error:** If the model still calls `write_file` before approval, the existing red tool card remains. Stopping that call is the job of the prompt plus the questionnaire latch, not a new error string.

### Interaction Details

- One approval click on the card. The button stays "Approve".
- Fields the Discovery summary already settled are filled in. The person can change the name, direction, color, and visuals on the card.
- A rename on the card is the app name. Page contents stay the Discovery summary unless the person changes them in chat after approval.
- Non-factory chats keep today's questionnaire, then the same card.

### Accessibility

- The blueprint card is the existing card. No new control.
- The hex color stays text next to the swatch.
- Focus behavior of the current card is unchanged.

## Technical Design

### Architecture

The gate stays. `assertAppBlueprintApproved` still throws when this chat has no approved blueprint. What changes is how an Implementation chat is allowed to create that blueprint, and what the phase prompt tells the model to do first.

`write_app_blueprint` refuses the first blueprint unless `ctx.appBlueprintQuestionnaireCompleted`. That flag is true only when this chat's messages contain a successful `planning_questionnaire` tool result (`hasCompletedAppBlueprintQuestionnaire`). Implementation is a new chat, so the flag is false and a prompt that only says "call `write_app_blueprint`" still throws and stores nothing. The prompt change and the latch are both required.

### Components Affected

- `src/lib/factoryPhase.ts` — add `factoryPhaseSkipsBlueprintQuestionnaire(phase)`, true only for `"implementation"`.
- `src/prompts/factory_phase_prompt.ts` — Implementation's first action is `write_app_blueprint`, then stop. After the approval follow-up, build the page and end with the Implementation summary. Discovery and Delivery text stay as they are.
- `src/pro/main/ipc/handlers/local_agent/local_agent_handler.ts` — when the chat title is the Implementation phase and the app still needs a blueprint, set `ctx.appBlueprintQuestionnaireCompleted` true even if this chat has no questionnaire result.
- `src/ipc/handlers/chat_stream_handlers.ts` — pass the same latch into `constructSystemPrompt` so the blueprint block does not still demand a questionnaire.
- `src/prompts/local_agent_prompt.ts` — only if the system-prompt block still says the questionnaire happened "in this chat" after the latch is true. The factory appendix must say the Discovery summary replaces it.

Unchanged: `tool_invocation.ts`, `execute_sandbox_script.ts`, `app_blueprint_handlers.ts`, `plan_handoff/definition.ts`, and the blueprint card component.

### Data Model Changes

None. The blueprint stays in the in-memory map keyed by the Implementation chat id. Approval still sets `apps.needsAppBlueprint` to false, then marks the in-memory plan approved. A restart before approval still drops the card. The next `write_file` fails until the model writes the blueprint again. That restart gap is accepted for this change.

### API Changes

No new IPC channel and no new tool. Reuse `appBlueprintQuestionnaireCompleted`.

The latch is true only when all of these hold:

- The chat title maps to the Implementation phase (`phaseFromTitle`).
- `settings.enableAppBlueprint && app.needsAppBlueprint` is still true.
- The user message for this turn contains an approved Discovery summary (the Continue prefill, or a summary that `extractFactoryPhaseSummary` can read as Discovery).

A renamed chat whose title is no longer "Implementation" does not get the latch. An ordinary build chat does not get it.

## Open Questions

- None that block the change. If a later pass wants factory apps to skip the card entirely, that is a product change to `needsAppBlueprint` at app creation, not a tweak to this latch.

## Decision Log

- Implementation owns the blueprint. Discovery is Ask-only and must not collect templates or stacks. Delivery does not write files. The card is stored on the Implementation chat id, so a Discovery summary cannot satisfy `getAppBlueprintForChat`.
- Do not skip the card for factory apps. Color, design direction, and planned visuals were never in the Discovery approval. Writing files first would hide those choices. The factory Continue button approves the brief. The blueprint card approves the look.
- Do not add a second `planning_questionnaire`. The approved Discovery summary is the questionnaire for this chat.
- Keep `assertAppBlueprintApproved`. A prompt-only change cannot store a blueprint, because `write_app_blueprint` still throws without the questionnaire latch.
- Do not change plan handoff. Accepting a plan already clears `needsAppBlueprint`.
