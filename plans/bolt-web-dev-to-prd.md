# Bolt as the website, from dev to production

> Generated by swarm planning session on 2026-10-07

## Summary

Stop hosting the Dyad desktop app as a website. Use the existing [Awannaphasch2016/bolt.diy](https://github.com/Awannaphasch2016/bolt.diy) fork, which is a browser app, and put only the factory walkthrough already built in Dyad on top of it. Promote that one flow from a local Docker dev server to a production container. Add Gas City after the walkthrough is stable. Remove the Dyad public URL after Gas City calls bolt.

## Problem Statement

End users need a website they can keep open. Dyad is an Electron app. The public preview carries its private IPC bus through Cloudflare, and that proxy closes a quiet socket. Upstream Dyad does not ship a hosted website, and no other public fork does either. bolt.diy is already a website: chat, files, and a live preview run in the browser. The fork is an exact copy of `stackblitz-labs/bolt.diy` as of 2026-10-07, so none of the Dyad factory work is in it yet.

## Scope

### In Scope (MVP)

The screen the Discovery walkthrough already uses:

- One chat. One send at a time. A second send waits until the first reply finishes.
- Three phases in order: Discovery, Implementation, Delivery. The later phase stays locked until the current one is approved.
- Discovery asks for the page name, one sentence, and what is on the page. A short questionnaire is allowed. The approve button turns on only when the last assistant message contains a `## Discovery summary` heading and a bullet list for those three facts.
- Implementation receives that approved summary as the next prompt, builds one page, and shows it in the preview beside the chat.
- Delivery writes a `## Delivery summary` with bullets. Approve finishes the run.
- A one-line comment box on the current phase.
- Dev runs with `docker compose --profile development up`. Production runs the existing `app-prod` service from `docker-compose.yaml`.
- The model key lives in the server environment for production. The person using the site does not paste a provider key to start the walkthrough.

### Out of Scope (Follow-up)

- The Electron browser bridge, the Cloudflare websocket, and the Namespace preview tunnel.
- Porting Dyad IPC, the desktop preview pane, or the terminal-through-Electron path.
- bolt.diy features that are not in the Dyad walkthrough: speech input, MCP tools, Supabase connect, Netlify and Vercel deploy buttons, GitHub import, starter-template gallery, and the optional Electron desktop build.
- Clerk organizations, role gates, and the full Gas City question API. A single production site is enough until the walkthrough is stable.
- Git-repo repair, app-row cleanup, and the other desktop filesystem fixes. Those belong to the Electron app.

## User Stories

- As a person opening the site, I want to describe one page and see it, so I do not install a desktop app.
- As a person in Discovery, I want the next phase to stay locked until the summary is posted, so I approve a finished brief.
- As a person who approved Discovery, I want Implementation to start from that summary and show the page, so I can tell if it is right.
- As an operator, I want the same container in dev and production, so promotion is a profile and an environment change.

## UX Design

### User Flow

1. Open the site. The chat is on Discovery. Implementation and Delivery are locked.
2. Send one message, for example "Bartel coffee". The composer ignores another send until the reply ends.
3. Answer the short questionnaire in the thread.
4. When the reply contains `## Discovery summary` and the three bullets, **Approve and continue to Implementation** enables.
5. Approving opens Implementation and sends the summary as the build prompt. The preview shows the page as files land.
6. **Approve and continue to Delivery** enables after `## Implementation summary` and its bullets.
7. Delivery posts `## Delivery summary`. **Approve delivery** ends the run.

The phase hint text already written in `src/lib/factoryPhase.ts` stays the copy:

- Discovery: ask for the page name, one sentence, and what goes on the page. Approve once the Discovery summary looks right.
- Implementation: send the prefilled summary, review the preview, approve when the page looks right.
- Delivery: summarize what was built. Approve when the trial is finished.

### Key States

- **Default**: Discovery selected, later phases locked, composer ready.
- **Loading**: the reply streams in the thread. The composer shows that a turn is in progress. The approve button stays off.
- **Empty**: a new run has no messages. The hint under the phase bar tells the person what Discovery needs.
- **Error**: a failed turn shows the error in the thread and re-enables the composer. The phase does not advance.

### Interaction Details

The phase bar sits above the chat, matching `src/components/chat/FactoryPhaseBar.tsx`: three phase controls, the approve button on the right, then the comment field. Locked phases do not navigate. The summary parser is the one in `src/lib/factoryPhase.ts`: a heading of `## <Phase> summary` followed by bullets. Text inside a thinking block does not count. An ordinary reply does not unlock approve.

The preview is bolt's existing workbench preview. It is visible on Implementation and Delivery. Discovery is chat only.

### Accessibility

Phase controls are buttons with the phase name as the accessible name. A locked phase exposes that it is unavailable. The approve button's accessible name is "Approve and continue to Implementation", "Approve and continue to Delivery", or "Approve delivery". The comment field keeps the label "Phase comment".

## Technical Design

### Architecture

bolt.diy stays the application. It is a React Router app served by Vite, with WebContainers running the generated project in the browser. Chat already lives in `app/components/chat/BaseChat.tsx`. The factory bar is a new component beside that chat. It does not talk to Electron.

Dev and production are the two profiles already in `docker-compose.yaml`:

- `app-dev` runs `pnpm run dev --host 0.0.0.0` on port 5173 with the repo mounted.
- `app-prod` runs the `bolt-ai-production` image and `pnpm run dockerstart` on port 5173.

Promotion is: the walkthrough passes on `app-dev`, then the same commit is built as `app-prod` with production environment variables. No second codebase.

Dyad remains the Gas City backend until the bolt walkthrough is the one on the production URL. The port 32100 factory host in `src/main/factory_host_bridge_server.ts` is the contract to copy later, not the thing to expose from Dyad.

### Components Affected

Work happens in the bolt.diy repo, not in this Dyad tree:

- `app/components/chat/BaseChat.tsx` — mount the phase bar and block a second send while a turn is streaming.
- `app/components/chat/Messages.client.tsx` — render the questionnaire block already returned in the assistant message.
- New `app/components/factory/FactoryPhaseBar.tsx` — the three phases, the approve button, and the comment field. Behavior copied from Dyad's `src/components/chat/FactoryPhaseBar.tsx` and `src/lib/factoryPhase.ts`.
- New `app/lib/factoryPhase.ts` — the phase order, the summary parser, and the unlock rules. Copy the pure functions. Leave the Electron imports behind.
- The Discovery system prompt in bolt's chat API route — the three questions and the exact `## Discovery summary` shape from `src/prompts/factory_phase_prompt.ts`.
- `docker-compose.yaml` — unchanged profiles. Production env file gains the one model key and nothing else required for the walkthrough.

### Data Model Changes

A run stores, in bolt's existing project storage:

- `phase`: `discovery`, `implementation`, or `delivery`
- `approved`: the set of phases already approved
- `comments`: `{ phase, body }[]`
- The summary text parsed from the last assistant message. It is not a separate record. Reload reads the messages again.

No Neon schema and no Dyad sqlite in this cut.

### API Changes

None for the first production cut. The browser and the bolt server already stream the chat.

After the walkthrough is stable, add three routes that match the Gas City calls Dyad already serves:

- `POST /v1/apps/:id/phases/:phase/messages`
- `POST /v1/apps/:id/phases/:phase/approve`
- `POST /v1/apps/:id/phases/:phase/runs`

Those routes stay out of the first production image.

## Open Questions

- Which single model key production uses. Any provider bolt already supports is fine. Pick one and keep it in the production env.
- The production hostname. It can wait until Phase 3. Dev does not need it.

## Decision Log

- bolt.diy is the website. Dyad's Electron bridge is not ported. The public-URL failures came from putting a desktop IPC bus behind Cloudflare.
- The fork has no local commits yet. The first work is the factory walkthrough, not a rebase or a rewrite.
- Only the UI already used in the Dyad walkthrough is in scope: phase bar, one send, questionnaire, summary gate, preview, comments. bolt's extra panels stay out of this flow.
- Dev and production are the two compose profiles already in bolt.diy. Promotion is the same commit with the production profile.
- Gas City moves after production can run the walkthrough. Dyad's port 32100 stays until then.
- Product principles: the generated page stays ordinary web code (Productionizable). The phase gate shows the summary before approve (Transparent). The site is the common path; provider keys and deploy targets stay out of it until later (Intuitive). One provider env var keeps the first production site from depending on a second account system (Backend-Flexible).
