# Show the generated site in the lab preview

> Generated by swarm planning session on 2026-10-08

## Important points

- The bakery site is already saved. The preview pane never shows it.
- The pane keeps asking one address whether a page is ready. A normal website fails that check, so the pane waits and retries.
- Writing more files does not change that address. Only another deploy replaces the saved snapshot.
- The fix serves that snapshot as a normal website, and shows a clear stop when there is still no page.
- The lab stays one worker. No separate public site per generated app, no sandbox container, and no change to Dyad’s preview.

## Summary

After the lab builder says Deployed, the preview pane should show the website that was just saved. Today it retries a check that a normal site cannot pass. The lab will serve the saved HTML, CSS, and images from the existing preview address, and the pane will stop immediately when that snapshot still has no page.

## Problem Statement

A person asks for an ordinary website, such as a neighborhood bakery. The builder writes the files and the chat shows Deployed, with Rollback when the save includes a commit. The right pane stays on Loading Preview and counts retries until it gives up.

The site was saved. The preview cannot show it. The pane treats every failed check as “still starting,” including a failure that will never change. Deployed next to a spinner is worse than a clear miss, because the product has already said the site is ready.

## Scope

### In Scope (MVP)

- Serve a normal website from the snapshot that Deployed already stored.
- Make the preview’s readiness check succeed for that page.
- When the snapshot has no page, stop on the first answer and say the preview cannot show it.
- Keep apps that already preview through a Worker `App` class on their current path.
- Apply the change in the lab deploy, the same way the lab already patches the Vibe SDK checkout.

### Out of Scope (Follow-up)

- A public address for each generated app.
- Workers for Platforms, a dispatch namespace, or a sandbox container.
- The headless browser console tool. This lab has no browser binding, and the page can be shown without it.
- Building Vite, Next, or other framework projects before preview.
- Single-page fallback, where unknown paths return `index.html`.
- Showing files that are still being written, before the next deploy.
- Dyad’s `preview` label, `preview.yml`, `build.cloudflare.dev`, and production Vibe SDK resource ids.

## User Stories

- As a person who asks for a neighborhood bakery, I want the preview pane to show that site after Deployed, so I can judge the result instead of watching a spinner.
- As that person, I want the page, its stylesheet, and its images to load, so the site looks like the one that was saved.
- As a person whose snapshot has no page, I want the pane to stop and say so, so I do not wait through ten retries.
- As a person who later hands the project to someone else, I want ordinary HTML, CSS, and JavaScript, so they can maintain it without this lab.

## UX Design

### User Flow

1. The person sends a prompt. The right pane stays a quiet placeholder until a preview address exists.
2. The chat reaches Deployed. The pane says it is opening that address and requests it once.
3. The bakery page appears in the pane. The overlay goes away.
4. If the check cannot connect, or the worker is briefly unavailable, the pane may try again a couple of times over a few seconds. There is no attempt counter and no eight-second countdown.
5. A lasting miss uses the existing error state immediately. The title is Preview not available. One sentence says what happened. The only action is Try again, which reloads the same address.
6. Another Writing step in the chat does not change that address. Try again still reloads the saved snapshot.

### Key States

- **Waiting**: No preview address yet. Short placeholder. No spinner and no countdown.
- **Opening**: Address exists and the first check is in flight. Neutral spinner. No footnote about URLs taking a moment.
- **Site**: The check succeeded. The website fills the pane.
- **Not available**: The snapshot answered 401, 403, 404, or 500, or a short start window passed. Existing error layout, one sentence, Try again.
- **Couldn’t display**: The frame itself fails after the page was shown. This stays separate from a failed check.

### Interaction Details

- The spinner runs only while a request is in flight.
- A simple site either appears or explains itself shortly after Deployed.
- Try again does not restart a tour of ten attempts.
- The pane does not ask the person to describe the problem in chat. That path is what sends the builder into a second write that the preview is not showing.
- Opening uses a calm treatment. The error state is the one that looks like a warning.

### Accessibility

- One polite live region announces Opening preview, Preview still starting, and Preview not available. A countdown is not announced.
- The spinner is hidden from assistive tech. The text carries the state.
- Try again keeps a visible name, a focus ring, and a tab stop. Failure does not steal focus from the chat.
- The frame is not in the tab order until the site is shown.
- Reduced motion stops the spin. The status text stays.

## Technical Design

### Architecture

The lab checks out Vibe SDK at `9da158d82c597a0e8f4bf033cdccd1053fb6fb15` and patches it before deploy. This fix is three patches in that same style. Each patch throws if its anchor is missing, so a drifted checkout fails before Wrangler runs.

The preview address stays `/space/<app>/preview/<branch>/`. Signed `?t=` access, the preview cookie, and the rate limit stay as they are. The pane reads the last deploy snapshot, not the files the builder is editing.

1. **Store a normal site in the snapshot.** When the commit has no `export class App`, copy its web files into the snapshot’s existing asset map: HTML, CSS, JS, and common image and font types. Skip `.git`, `node_modules`, dotfiles, and everything else. Set HTML handling so `/` resolves to `index.html` when that file is present. A commit that already has `export class App` keeps today’s Worker bundle and is not replaced by this copy.
2. **Serve that map.** Keep serving declared asset files first. Load `class App` only when the asset map does not answer the path. If that class is missing and the map has files, serve the file or `index.html` for a document request. If the map is empty and the class is missing, return a plain 404. Do not invent an `App` class. A real `App` class that fails to load stays a 500. It does not fall through to static files.
3. **Let the readiness check succeed.** The pane uses `HEAD`. A static HTML response to `HEAD` has no body. Skip HTML rewriting in that case and return the status and content type unchanged. Keep HTML rewriting for `GET`, so links such as `/style.css` still point at the preview path.
4. **Stop retrying a finished failure.** `401`, `403`, `404`, and `500` open the error pane on the first answer. A `200` with no preview-type header still counts as ready. A network failure or timeout may retry briefly. `sandbox-error` keeps its current retry. A `503` is shown as an error rather than ten retries. The silent redeploy that fires around attempt 8 does not run for these finished failures.

### Components Affected

- `scripts/doppler/vibesdk-lab.mjs` — the three patch functions.
- `scripts/doppler/deploy-vibesdk-lab.mjs` — apply them to the checkout.
- `scripts/doppler/vibesdk-lab.test.mjs` — fixture tests.
- Checkout only, at deploy time: `space/src/space/deploy-engine.ts`, `space/src/space/durable-object.ts`, `src/routes/chat/components/preview-iframe.tsx`.

The per-PR Vibe SDK provisioner applies these same patches, together with the app-creation limit already used by the lab. That change lives on `cursor/preview-backend-plan-fd29`. It does not go into Dyad’s `preview.yml`.

### Data Model Changes

None. The snapshot remains the existing deployment row. A normal site fills the asset map that row already has.

### API Changes

No new route. `GET` and `HEAD` of the existing preview path change as follows:

- `HEAD` of a stored HTML document returns 200 with a content type and an empty body.
- A snapshot with no `App` class returns the stored file, or a plain 404, instead of “Failed to load App class.”
- A path that is not in the asset map, including `/api/*` on a static snapshot, is a 404.

## Risks & Mitigations

| Risk                                                            | Likelihood | Impact | Mitigation                                                                                                               |
| --------------------------------------------------------------- | ---------- | ------ | ------------------------------------------------------------------------------------------------------------------------ |
| The builder emits a framework project with no `index.html`      | Medium     | High   | The pane stops on 404. Framework builds stay out of this change.                                                         |
| Copying the snapshot serves a secret or a dotfile               | Medium     | High   | Copy only web file types. Skip dotfiles, `.git`, and `node_modules`. Unknown paths 404.                                  |
| A failing Worker app is hidden by the static fallback           | Low        | High   | The fallback runs only when no file contains `export class App`.                                                         |
| `HEAD` stays 404 while `GET` would succeed                      | Medium     | High   | The static path answers `HEAD` with the same success as `GET`, and HTML rewriting is skipped only when there is no body. |
| Skipping HTML rewriting for every response breaks styles        | Medium     | Medium | Rewrite `GET` HTML. Skip the rewriter only for an empty body.                                                            |
| The checkout anchor moves and the patch matches the wrong block | Low        | High   | Each patch throws when its anchor is missing or still present after the edit. The lab deploy fails before publish.       |

## Open Questions

- A framework prompt may still produce no `index.html`. The pane will say the preview cannot show that snapshot. Whether the builder should be steered toward a single HTML file can be decided after the bakery path works.
- External fonts and images are not part of this fix. The page and its same-snapshot files are the success bar.

## Decision Log

- Serve the saved files. Do not require the builder to emit `export class App`, and do not change the prompt in this change. A normal site is what a person can hand to someone else.
- Do not read the working tree on a preview request. Writing more files still does not change the address. Only a deploy replaces the snapshot.
- Do not fall through from a broken `App` class to static files.
- Do not show the frame before the check succeeds. Fix the check, and stop treating a finished failure as loading.
- Retry only a dropped connection, a timeout, or `sandbox-error`. Finished HTTP errors stop immediately.
- Do not add a browser binding, a container, a dispatch namespace, or a per-app public URL.
- The per-PR provisioner gets the same patches. Dyad’s preview workflow stays Dyad-only.
