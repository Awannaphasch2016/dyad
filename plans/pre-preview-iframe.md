# Serve the canary app preview on a public hostname

> Generated by swarm planning session on 2026-10-08.
> The white pane was observed on `https://pre.anakwannaphaschaiyong.com` while task `wewebplus-canary:7` was running. The preview proxy had bound `http://localhost:42103` inside the container.

## Summary

The preview pane goes white because the iframe points at `http://localhost:42103`, an address that exists only inside the canary container. The fix keeps that proxy where it is and gives the browser an HTTPS hostname on the same tunnel, so the iframe loads the user's app. The generated app stays on its own origin, separate from the Dyad page and its sign-in cookies.

## Problem Statement

A person testing on pre can watch "Preparing preview" and the install log, which are drawn by the Dyad page. When the dev server is ready, Dyad hides that screen and sets the preview iframe to the proxy URL the main process reported, `http://localhost:42103`. That URL was logged at 14:12 UTC, the same moment the pane turned white.

The browser showing the page is the phone or laptop, not the container. `localhost:42103` is the container's loopback. The page is HTTPS, so the browser also refuses the HTTP frame. The iframe's background is white, which is the blank pane. The Cloudflare tunnel only forwards `pre.anakwannaphaschaiyong.com` to port 8373. The security group has no public ingress, so the proxy port is not reachable any other way.

The desktop app does not have this bug. There, the iframe and the proxy run on the same machine.

## Scope

### In Scope (MVP)

- On the public canary page, the preview iframe loads the app that is already running on the container's preview proxy.
- HTTP and WebSocket (Vite refresh) both go through the existing tunnel to port 8373, then to `127.0.0.1` on the proxy port.
- The app's origin is not the Dyad page's origin.
- A request for any port outside the preview-proxy band is refused.
- The desktop app still loads `http://localhost:<proxy port>`.
- The apex name, `gascity-server`, and the production database are unchanged. No new public port is opened.

### Out of Scope (Follow-up)

- Preview environments on `pr-<n>.anakwannaphaschaiyong.com`. The same host rule can be reused later. This plan rolls it out on pre only.
- Visual editing that needs to read the iframe document. The iframe is already a different origin from the Dyad page in a normal browser. postMessage keeps working.
- A generated app whose own React tree renders an empty page. That is an app bug, not this routing bug.
- Promotion, Doppler database URL changes, and opening 32100, 6080, or 8373.

## User Stories

- As a person testing a build on pre, I want the preview pane to show the app after install finishes, so that I can see what the chat just built.
- As that person, I want a failed app server to show an error in the pane, so that a blank white page is not the only signal.
- As the operator, I want the generated app unable to read the Dyad sign-in cookie, so that a bad build cannot act as me.

## UX Design

### User Flow

1. The user sends a chat on `https://pre.anakwannaphaschaiyong.com` and the app starts.
2. The preview pane stays on "Preparing preview" and streams the install log, as it does today.
3. When the proxy is listening, the iframe address becomes `https://<port>.apps.pre.anakwannaphaschaiyong.com/`.
4. The pane shows the user's app. Later edits refresh through the existing proxy WebSocket.
5. The user does not copy a URL or pick a port. Refreshing the Dyad page is enough to pick up the new iframe address.

### Key States

- **Loading**: "Preparing preview" stays up until the iframe address is the public hostname. The pane does not swap to a white frame while the address is still `localhost`.
- **Ready**: The iframe fills the pane with the app. The toolbar and address path stay as they are today.
- **Empty**: No selected app. The pane stays on the current empty preview state.
- **Error**: If the proxy is down, the bridge answers 502 and the pane shows that failure instead of a silent white page. A crashed app process still uses the existing preview error banner.

### Interaction Details

No new control. The address shown in the toolbar can stay the in-app path (`/`, `/about`). The public hostname is an implementation detail, not a second place the user has to manage.

On a phone, the pane is the same iframe, so scrolling and tapping go to the app.

### Accessibility

The iframe keeps its current title (`Preview for App <id>`). A 502 page is text, so a screen reader can read it. The loading screen's existing live region continues to announce "Preparing preview".

### Consistency notes

This matches the desktop preview: one pane, one app, install log then the app. The only change is the address the browser is allowed to open. Product principle "Delightful" is the live preview itself. A white pane after a successful install breaks that loop. "Transparent Over Magical" means a dead proxy shows an error, not an empty white box.

## Technical Design

### Architecture

The preview proxy in `worker/proxy_server.js` already listens on `127.0.0.1` in the band `42100..52149` and already tunnels WebSocket upgrades to Vite. It stays the process the iframe talks to. What changes is the public name in front of it.

```
phone browser
  iframe  https://42103.apps.pre.anakwannaphaschaiyong.com/
    → Cloudflare tunnel (existing cloudflared, still only port 8373)
    → browser bridge
    → http://127.0.0.1:42103/     (dyad preview proxy)
    → http://127.0.0.1:32103/     (the user's Vite server)
```

The hostname carries the port so the app is served at `/`. Vite asset URLs and the refresh socket stay on that host. A path prefix on the Dyad host would make the generated app same-origin with the shell, because the iframe is sandboxed with `allow-same-origin`, and it would also break Vite's absolute paths.

Cookie rule: a cookie set on `pre.anakwannaphaschaiyong.com` with no `Domain` attribute is not sent to `42103.apps.pre.anakwannaphaschaiyong.com`. The apps hostname is not added to Clerk's allowed origins.

Desktop rule: when the page hostname is `localhost` or `127.0.0.1`, the iframe src stays the localhost proxy URL.

### Components Affected

- `src/preview_iframe/public_preview_url.ts` — new pure helpers. `publicPreviewUrl(pageUrl, proxyUrl)` returns the apps hostname for a public page and the original proxy URL for localhost. `previewPortFromHost(host)` returns the port only when the host is `<port>.apps.<parent>` and the port is inside the proxy band.
- `src/components/preview_panel/PreviewIframe.tsx` — iframe `src` uses `publicPreviewUrl`. postMessage target origin uses that same public origin, so messages are not still aimed at `http://localhost:42103`.
- `src/main/browser_bridge.ts` — before serving the Dyad renderer, if the `Host` header is a preview hostname, proxy the HTTP request and the WebSocket upgrade to `127.0.0.1:<port>`. Any other host is unchanged. The Dyad socket path `/dyad-browser-ipc` stays on the Dyad hostname only.
- `deploy/canary/tunnel.mjs` — ingress gains `*.apps.pre.anakwannaphaschaiyong.com` → `http://127.0.0.1:8373`, listed before the 404 rule. DNS gains one proxied CNAME for that wildcard to `<tunnel-id>.cfargotunnel.com`. `assertCanaryHostname` grows an allowlist for that wildcard only. The apex check stays.
- `deploy/canary/tunnel.test.mjs` and `src/main/browser_bridge.test.ts` — the cases below.

### Data Model Changes

None. The stored preview URL in the main process stays `http://localhost:42103`. Only the iframe address the browser navigates to is rewritten.

### API Changes

No IPC channel is added. The bridge's HTTP behavior grows one host rule.

Port allowlist, from `shared/ports.ts`:

- Accept `42100..52099` (proxy band) and `52100..52149` (fallback band).
- Refuse everything else, including `32100` (app / factory), `6080`, `5900`, and `8373`.

A refused host gets 404. A refused or dead upstream gets 502. The bridge must not follow the port to an arbitrary container service.

### Why not the other approaches

| Approach | Why it is not the fix |
| --- | --- |
| Open port 42103 on the security group | The pane would still be mixed content (`https` page, `http` iframe), and the port would be public. |
| Path on `pre.anakwannaphaschaiyong.com` | Same origin as the Dyad shell, so the app could read the sign-in cookie. Vite would request `/src/...` without the prefix. |
| Point the iframe at the Vite port `32103` | Skips the preview proxy, so the injected preview scripts and the WebSocket tunnel in `worker/proxy_server.js` are bypassed. |

## Risks & Mitigations

| Risk | Likelihood | Impact | Mitigation |
| --- | --- | --- | --- |
| Wildcard DNS is rejected by the zone plan | Medium | High | Stop. Do not open a port. Fall back to one allowlisted CNAME per live proxy port. |
| Preview host is same-origin with the Dyad page | Low | High | Port is a hostname label under `apps.pre`, not a path on `pre`. Clerk origins do not gain the apps host. |
| Bridge proxies a non-preview port | Low | High | Allowlist is the proxy band only. Tests refuse `32100` and `8373`. |
| Vite refresh socket still points at localhost | Medium | Medium | The page is served from the apps host at `/`, and the existing proxy already tunnels `Upgrade`. The bridge must tunnel `Upgrade` too. |
| Tunnel update replaces the pre hostname | Low | High | Ingress is a list that still contains `pre.anakwannaphaschaiyong.com` first. The apex write stays refused. |

## Decision Log

- The white pane is an unreachable iframe, not a crashed Vite server. The proxy was listening on `127.0.0.1:42103` when the pane went white.
- The public address is `https://<port>.apps.pre.anakwannaphaschaiyong.com/` so the app stays at `/` and on a different origin from the Dyad page.
- Traffic enters through the existing tunnel and port 8373. The security group stays closed.
- Desktop localhost behavior is unchanged.
- A path on the Dyad hostname was rejected because of cookie access and Vite absolute URLs.
- Publishing the proxy port was rejected because of mixed content and the closed security group.
