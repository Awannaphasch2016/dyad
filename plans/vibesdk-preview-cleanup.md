## Summary

Reviewers already get a Vibe SDK preview by adding `preview-vibesdk` to an open pull request. The same URL is updated on later pushes and deleted when the label is removed or the pull request closes. This plan makes that delete finish, and makes the pull request comment match what happened. The hostname stays the Cloudflare `workers.dev` name.

## Problem Statement

A reviewer needs one public Vibe SDK address for a pull request, and needs that address and its database to disappear with the pull request. The control path already does that. Teardown is not yet trustworthy, and the comment can claim a preview was removed when none existed.

No pull request has carried `preview-vibesdk` yet, so this can be fixed before the first preview is created.

## Scope

### In Scope (MVP)

- Keep the current decision table, resource names, and URL.
- Delete an existing Worker with `?force=true` on the first request, so its Durable Object namespaces are deleted with the script.
- Keep D1, KV, and R2 delete as it is: missing is success, and `force=true` is used only when Cloudflare rejects the first delete.
- Post Removed only when this run deleted at least one of those resources.
- When a cleanup-failed comment is already on the pull request and a later run finds nothing left, replace that comment with Removed.
- On destroy failure, update the same comment to say cleanup did not finish.
- Add a manual workflow run that takes a pull request number and runs the same delete. It uses the same per-pull-request lock and does not cancel an in-flight deploy.
- Check the destroy job out from the workflow ref, so a deleted head branch cannot block cleanup.
- Record in code that the two rate-limit counters are not deleted.

### Out of Scope (Follow-up)

- Any custom domain, including `pr-<number>.anakwannaphaschaiyong.com` and `vibesdk-pr-<number>.anakwannaphaschaiyong.com`.
- Renaming `preview`, or adding `preview-dyad` or `preview-cloudflare`.
- Bolt.
- A scheduled sweep of leftover Workers.
- Changing rate-limit ids, or deleting them.
- The lab worker, Dyad’s `preview.yml`, Neon, and production resource ids.
- Skipping the destroy job on a close that never had a preview. The job stays, finds nothing, and posts nothing.

## User Stories

- As a reviewer, I add `preview-vibesdk` to an open pull request so the comment shows `https://vibesdk-pr-<number>.karant-test-egress-canary.workers.dev`.
- As a reviewer, I push while that label is on so the same address serves the new commit.
- As a reviewer, I remove the label, or I close or merge the pull request, so the Worker, its Durable Objects, D1, KV, and R2 are deleted and the comment says Removed.
- As a reviewer, I close a pull request that never had this label so the thread stays quiet.
- As a maintainer, I rerun cleanup with the pull request number when the first delete failed, without reopening the pull request.

## UX Design

### User Flow

1. The reviewer adds `preview-vibesdk`. One comment appears: the preview is provisioning.
2. Deploy succeeds. That same comment becomes the `workers.dev` URL.
3. A later push keeps that URL.
4. Removing the label, or closing the pull request, changes the comment to Removed after the resources are gone.
5. If delete fails, the comment says cleanup did not finish and names the URL that may still be open.
6. A maintainer runs the workflow with the pull request number. A later success changes the comment to Removed.

### Key States

- **Absent**: No label and no preview comment. Closing the pull request adds nothing.
- **Provisioning**: “Vibe SDK preview is provisioning.” No URL yet.
- **Ready**: “Vibe SDK preview:” plus the `workers.dev` URL.
- **Deploy failed**: “Vibe SDK preview was not updated.”
- **Removed**: “Removed Vibe SDK preview” plus the URL that was deleted. Posted only after a real delete, or after a cleanup-failed comment when a later run finds nothing left.
- **Cleanup failed**: “Vibe SDK preview cleanup did not finish.” The URL stays in the comment.

### Interaction Details

The label is the control. The comment is the status. One comment is edited in place. The current status is the first sentence. A URL appears after a successful deploy and remains in the Removed and cleanup-failed comments so the address that was used is still visible.

Dyad’s `preview` label does not write this comment. Its URL stays in the Actions log.

### Accessibility

The status is a sentence. The address is the full URL, so it is a real link. The HTML marker stays in an HTML comment. Status is not conveyed by color or emoji.

## Technical Design

### Architecture

`commandForPullRequest` is unchanged. Close and merge still mean destroy even when the label is already gone, so a preview is not kept because the label disappeared in the same event. The comment gate is what changes: a destroy that deletes nothing, and has no cleanup-failed comment to correct, posts nothing.

The Worker delete becomes `DELETE /accounts/{account}/workers/scripts/vibesdk-pr-<number>?force=true` when the script exists. A 404 remains success and issues no delete. D1, KV, and R2 keep their current helper. `force=true` is not added to that shared helper, because a URL that already has the query would be doubled, and those resources do not need it on the first try.

`down` reports whether any of the four resources was deleted. The workflow posts Removed only in that case, or when it is correcting a cleanup-failed comment after a run that finds nothing left.

`workflow_dispatch` takes the pull request number and runs destroy. Deploy and destroy share `vibesdk-preview-pr-<number>` with `cancel-in-progress: false`. A manual retry waits for an in-flight deploy of that same pull request.

Rate-limit namespace ids stay `${pr}01` and `${pr}02`. Cloudflare’s Workers rate limiting binding has no list or delete API. The lab uses `2101` and `2102`, which are the ids pull request 21 would compute. Cleanup must not delete by those ids.

### Components Affected

- `deploy/preview/vibesdk-cloudflare.mjs` — Worker delete always uses `?force=true`. A helper reports whether anything was deleted. A comment records the rate-limit leftovers.
- `deploy/preview/vibesdk-preview.mjs` — `down` publishes that flag. Dispatch with a pull request number runs destroy.
- `deploy/preview/vibesdk.mjs` — `previewCommentBody` gains the cleanup-failed kind. Names, `workers_dev`, and the routes rejection stay.
- `.github/workflows/preview-vibesdk.yml` — manual run input, destroy checkout from the workflow ref, Removed only when something was deleted, cleanup-failed comment on destroy failure.
- `deploy/preview/vibesdk.test.mjs` — fake Cloudflare client only.

Unchanged: `deploy/preview/transition.mjs`, `.github/workflows/preview.yml`, the lab worker, Neon, and the URL.

### Data Model Changes

None. Names stay derived from the pull request number. No inventory is added.

### API Changes

Cloudflare, on destroy only: the Worker delete gains `?force=true` whenever the script exists. No rate-limit, zone, or custom-domain call.

GitHub: one new comment sentence for a failed destroy. A manual workflow input `pr`.

## Decision Log

- Keep the existing lifecycle and the `workers.dev` URL. Custom domain naming is a preference, and `pr-<number>.anakwannaphaschaiyong.com` is already Dyad.
- Keep destroy-on-close even when the label is already gone. Silence the comment when nothing was deleted, instead of skipping the delete.
- Always force-delete the Worker. Do not force-delete D1, KV, and R2 on the first try.
- Do not delete rate-limit counters. There is no API for them, and the lab’s `2101` and `2102` collide with pull request 21.
- A manual workflow run is the retry. No schedule.
- The three planning views agreed on this slice. The product view wanted the rate-limit counters deleted; engineering found no delete API and the lab collision, so they stay.
