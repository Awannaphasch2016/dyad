# First methodology runs on the GIT Conference scope

> Generated by swarm planning session on 2026-10-14

## Summary

Run three Spec Kit variations once each, from the same Git project and the same frozen specification. The starting commit is the clean Spec Kit baseline, before any site was written. Each variation receives the same prompt material and is scored by the existing acceptance suite. A second iteration is not designed until that variation's verifier has reported.

## Problem Statement

The factory needs one methodology variation chosen from measured runs, not from the shape of a formula. One Spec Kit run already exists, and its follow-up exists only because that run failed four contact checks in a way no other agent is guaranteed to repeat. Planning that follow-up's Dockerfile change into the next experiment would hand every method a fix it has not earned, and it would treat one agent's output as the output of every agent.

## Scope

### In Scope (MVP)

- One first run for each of these Spec Kit variations:
  - Methodology-native: a Cursor agent on the implementation repo follows the Spec Kit skills already installed at the baseline (`speckit-specify`, `speckit-clarify`, `speckit-plan`, `speckit-tasks`, `speckit-implement`, `speckit-converge`).
  - Gas City-native: `speckit-build` orchestrates that same command order. Gas City runs the steps, drains, and fan-out. No phase gate is attached.
  - Three-phase HITL: `speckit-phased` keeps that order and adds the Discovery, Implementation, and Delivery human gates.
- Repository `Awannaphasch2016/sdd-gitcon-impl`, starting commit tag `baseline/speckit-1.1.2`.
- Specification `gitcon-v1` at sha256 `30916614bd4380d1a93c92432e9753f3038ecfacd6e976906332ad4086485127`, shipped to the worker as `SPEC.md`.
- Score: AC-01 through AC-20, the specification hash, and the leak scan, using the verifier from the harness branch.
- Isolated worktrees. One variation, one branch, one agent or city. Launched together.
- A gate closer for the phased run only. It writes `human_gate.verdict` on the confirmation bead. It approves when the artifacts that gate is waiting on are present. It does not invent product changes.

### Out of Scope (Follow-up)

- The text of any second iteration. That prompt is written after a verifier result, from the failed checks of that variation, and it starts from that variation's failed commit.
- Starting from `bc32948` or from `1b0784ea`. Those commits are the previous Spec Kit site and the Dockerfile rewrite. They are evidence, not inputs.
- OpenSpec, BMAD, Superpowers, gstack, Compound Engineering, and `build-basic`. Their first runs need a tree that does not already contain Spec Kit skills. This baseline does.
- The Next.js `gitcon-next-v1` plan.
- Merging an implementation pull request, or giving any worker `dev25-git-con` or `https://gitconference.git.or.th`.
- Changes to Dyad application code.

## User Stories

- As the person choosing a methodology, I want three first runs on one specification so that a pass or a failure belongs to that variation.
- As the person reading the result, I want the score to be the acceptance suite, so that a finished orchestration is not treated as a finished site.
- As the person who may ask for a follow-up, I want that follow-up to start from the commit that failed, so that the next agent continues the work that agent produced.

## UX Design

### User Flow

1. The coordinator copies `gitcon-v1` into `SPEC.md` on a new branch from `baseline/speckit-1.1.2`. The acceptance directory stays in the Dyad harness. The worker never receives it.
2. The variation runs in its own worktree until it stops or the cap is reached.
3. The verifier builds the Docker image, runs AC-01 through AC-20, checks the specification hash, and scans for leaks.
4. The report lists the AC table, the head commit, the verifier URL, and the counters that were actually recorded.
5. The reader compares the three reports. A variation with no verifier artifact has no score.

### Key States

- **Ready**: branch exists at the baseline, `SPEC.md` matches the hash, no agent has started.
- **Running**: the variation's agent or city is in progress. The other two are unaffected.
- **Scored**: verifier artifact is stored and the AC table is filled from that artifact.
- **Unscored**: the agent stopped, the cap was hit, or a gate stayed open. The report says so and leaves the AC cells empty.
- **Follow-up eligible**: at least one AC failed, the head commit is recorded, and no second prompt has been written yet.

### Interaction Details

The phased run's closer sends no product opinion. Discovery approves when `spec.md`, `plan.md`, and `tasks.md` exist under the artifact root and `spec.md` has no `NEEDS CLARIFICATION` marker. Implementation approves when the converge step has finished and the site files exist. Delivery approves when the final report exists. A missing artifact leaves the bead open. That run stays unscored rather than being patched by a prepared retry.

Clarify, when the formula asks, is answered from section 5 of `SPEC.md` and from the requirement tables. The answer adds no page, field, or service.

### Accessibility

The reports are Markdown tables with the AC id, status, and evidence path in text. A screenshot is evidence for AC-16. It is not the only record of a pass.

## Technical Design

### Architecture

Two executors share one repository, one baseline, and one verifier.

The native run reuses the harness pattern from [PR #99](https://github.com/Awannaphasch2016/dyad/pull/99): a Cursor cloud agent on `Awannaphasch2016/sdd-gitcon-impl`, Spec Kit skills from the baseline, then `.github/workflows/sdd-verify.yml` on the harness branch. The historical runs `2026-10-09-gitcon-v1-speckit-01` and `2026-10-10-gitcon-v1-speckit-02` stay in the record. They are not cells in this comparison.

The Gas City runs sling `speckit-build` and `speckit-phased` from `formulas/speckit`. Each sling gets its own rig whose worktree starts at `baseline/speckit-1.1.2`. `artifact_root` is the directory where that formula writes `spec.md`, `plan.md`, and `tasks.md`. `SPEC.md` at the repository root remains the frozen input and is not rewritten by the formula.

The verifier checks out the variation's head, builds `docker build -t sdd-site`, and runs the Playwright suite in `experiments/sdd/specs/gitcon/v1/acceptance/`. A pass still requires the specification hash and a clean leak scan.

### Components Affected

### Data Model Changes

One `run.json` per variation, in the harness run directory, recorded when the launch exists. Fields already used by the harness are enough: `run_id`, `approach`, `spec_sha256`, `impl_repo`, `baseline_ref`, worker ids, `pr.head_sha`, caps. No second-iteration fields are filled in advance.

Suggested run ids, assigned at launch, not before the branch exists:

- `gitcon-v1-speckit-native-01`
- `gitcon-v1-speckit-gascity-01`
- `gitcon-v1-speckit-phased-01`

### API Changes

None in Dyad. The native launcher is the existing Cursor agent create call. The Gas City launcher is `gc sling` on a local rig. The verifier remains the existing workflow.
