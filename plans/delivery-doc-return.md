# Restore the signed-in workspace when the browser tab closes

> Generated by swarm planning session on 2026-10-06. Revised twice the same day. Opening the delivery document on its own page stays as it is. The work in this plan is the return: the same sign-in, the same open chats, and the messages still in sqlite. A chat tab stays closed only when the person closed that tab.

## Summary

On iPad Safari, **Download documentation** replaces the preview tab with the HTML file. Coming back reloads `/chat` with the old chat and app ids. The page shows `DyadError: Chat not found`, `DyadError: App not found`, and a preview that waits forever for server logs.

Keeping the document inside the chat page does not fix that. The document may open as its own page. The next visit to this origin has to restore the workspace the person just left.

Two different closes exist.

- Closing a **chat tab** inside Dyad writes that chat id into `closedChatIds` in `localStorage` (`chat-tab-session-v2:<windowSessionId>`). That tab stays closed.
- Closing the **browser tab**, or Safari navigating that tab to the document, does not mean those chats were closed. The Clerk session cookie and that localStorage entry survive on the iPad. The next load must adopt them.

Today the next load does not. The socket close unregisters the bridge sender. The next bootstrap mints a new window id. `mayMigrateLegacyChatTabSession` is true only for the first Electron product window, so the iPad page skips `promoteMostRecentChatTabSession`. `restorableWindowSessionIds` is only those Electron window ids, so `pruneChatTabWindowSessions` deletes the iPad entry. The open tabs and the explicitly closed ids are both gone.

The next visit restores the Clerk session, the open chat tabs, the selected tab, and the messages still in sqlite. Explicitly closed chat tabs stay closed.

## Problem Statement

A person finished Noodle House on `https://pr-43.anakwannaphaschaiyong.com`. Implementation had saved `src/pages/Index.tsx`. In Delivery they tapped **Download documentation**. Safari replaced the pr-43 tab with the HTML document, so Dyad unloaded and the browser-bridge socket closed. About two minutes later they came back. The title was **No app selected**, the thread said **No messages yet**, the preview said **Preparing preview / Waiting for server logs…**, and the page reported `DyadError: Chat not found`, `DyadError: App not found` twice, and **Error loading proposal: Chat not found**. Noodle House was gone from the sidebar.

The download does not delete the chat. `downloadFactoryDocument` builds a `text/html` blob, clicks `<a download>`, and revokes the URL in the same turn. iPad Safari navigates the current tab to that blob. The return load still has `/chat?id=<chatId>&appId=<appId>`. `enforceSharedAccount` runs before the handlers. A missing chat row throws `DyadError("Chat not found")`. A missing app row throws `DyadError("App not found")`. The page selects those ids before the lookup, so the proposal query, the version query, and the preview all fail on their own.

Apps, chats, and messages live in the container sqlite on the compose volume `config:/home/weaver/.config` (`DYAD_DEV_USER_DATA_DIR=/home/weaver/.config/weaver-plus`). The schema-only Neon branch does not hold them. Closing the browser tab does not delete that file and does not sign the person out. Clerk's session cookie is on the iPad. `RequireSignedIn` redirects to `/sign-in` only when the session status is `signed-out`. While Clerk is loading it shows **Checking sign-in…**.

What the return loses is the memory of which chat tabs were open. `BridgeSender.noteSocketClosed` emits `destroyed`. `windowRegistry.unregister` drops that sender. The next `ensureRegistered` mints a new id because the sender id (`WEB_BRIDGE_SENDER_ID`) is no longer registered. Bootstrap then asks the product-window controller:

- `mayMigrateLegacyChatTabSession` is `productWindows.keys().next().value === windowSessionId`. The bridge id is not an Electron product window, so this is false. `src/renderer.tsx` skips `promoteMostRecentChatTabSession`.
- `restorableWindowSessionIds` is `[...productWindows.keys()]`. None of those ids are the iPad's `chat-tab-session-v2:` key, so prune deletes it.

The iPad localStorage and the Electron window's localStorage are different stores. Promote and prune run in the Safari page, against the iPad store, using flags computed from the Electron window list. A second Electron window must still refuse to adopt another window's tabs. The Safari return is the case that must adopt.

## Scope

### In Scope (MVP)

- **Download documentation** may keep opening the HTML as its own page. This plan does not add a dialog, a sandboxed frame, or a new save path.
- A chat tab the person closed stays in `closedChatIds` and does not come back as a tab.
- An accidental browser-tab close, or Safari leaving the chat URL to show the document, restores on the next load of this origin:
  - the Clerk session, with no sign-in step while that cookie is still valid
  - the open chat tabs and the selected tab
  - the explicitly closed chat ids, still closed
  - the app, the phase chats, and the messages that are still in this process's sqlite
- `/chat?id=&appId=` does not mount the chat or the preview until `getChat` confirms the row. A restored id that sqlite does not have is dropped from the open set. The other open tabs still come back. Those two guard messages do not toast on that load.
- When every restored id is missing, one card explains that and offers the home app list. That card does not recreate a missing chat. The person stays signed in.
- The guard strings stay. `assertChatVisible` and `assertAppVisible` still throw.

### Out of Scope

- Showing the delivery document inside the chat page. Opening it as its own page is acceptable once the return restores the workspace.
- The white Implementation preview. The toolbar was visible and **Preparing preview** was not, so the iframe had already been treated as ready. A later change can show **The preview page is blank** with **Reload preview** once a ready iframe has an empty document.
- Moving apps and chats into Neon, upgrading `postgres`, or restarting the container. Closing the tab is not a reason to start a new empty user-data directory. If a process is already on an empty sqlite, this change cannot invent the missing rows.
- Changing `src/main/browser_bridge.ts`, the disconnect toast, or the 500ms retry. Unregister on socket close stays. The return adopts the saved tabs after the new id is minted.
- Rewriting factory document HTML or adding a new IPC channel.
- Safari's own recently-closed-tabs list. Opening this origin again is what restores the workspace.

## User Stories

- As a person who opens the delivery document and then comes back, I want the same sign-in and the same open chats, so I do not redo Discovery, Implementation, or Delivery and I do not sign in again.
- As a person who closes the browser tab by mistake, I want that same return.
- As a person who closed a chat tab on purpose, I want that tab to stay closed after I come back.
- As a person who returns to a chat this server still has, I want that chat, the app, and the messages.
- As a person whose restored ids are gone from this server, I want one explanation and the list of apps that are still here. I understand the missing chat is not on that list. I am still signed in.

## What the person sees

### Flow A — the chat is still in sqlite

This is the flow that returns Noodle House. The card in Flow B is not part of it.

1. The person is signed in on Delivery for Noodle House. The chat tab is open.
2. They tap **Download documentation**. Safari may replace the tab with the HTML file. The Dyad page unloads. The Clerk cookie and the saved tab list stay on the iPad. The messages stay in sqlite.
3. They open `https://pr-43.anakwannaphaschaiyong.com` again, or they come back to the `/chat?id=&appId=` address.
4. They see **Checking sign-in…** while Clerk reads the cookie, then **Loading chats...** while the saved tabs are confirmed. The address is not replaced with `/sign-in`.
5. `getChat` finds the Noodle House chat. The page opens that chat. The thread shows the messages. The preview shows the app. Phase tabs that were open are open. A chat tab they had closed with the tab strip stays closed.
6. They continue from Delivery. They do not redo the earlier phases.

### Flow B — sqlite has none of the restored chats

This flow does not hand the missing chat back. It replaces the error popups and the endless preview spinner.

1. The person returns, still signed in, the same way as Flow A.
2. The saved list says "open chat 12." The server answers `Chat not found` or `App not found` for every id on that list. Those rows are absent from this process's sqlite.
3. The chat thread and the preview stay off the screen. One card is the whole page. Heading: **This app is not on this preview.** Body: **This link points at an app and chat this preview does not have.** One button: **Go to your apps.**
4. They tap **Go to your apps**. The address becomes `/`, the home screen. That screen lists the apps this preview still has in sqlite. It is the same list as the sidebar on a normal visit.
5. If Noodle House is one of those rows, it is on the list and they can open it from there. If Noodle House is absent from sqlite, it is absent from the list too. The button has no further step that recreates it.

"Your apps" means that home list. It does not mean a particular app chosen in advance.

## UX details

- **Returning:** **Checking sign-in…**, then **Loading chats...**. The composer and preview are not mounted yet.
- **Restored:** The same open chat tabs, the same selected tab, the same app, and the same messages. Closed chat tabs are absent from the tab strip and still listed in the sidebar.
- **The one card:** Only Flow B. It is an explanation that this server has no row for the chats the browser still remembers. The button leaves that dead address and opens the home list.
- **Empty home:** If sqlite has no apps at all, the existing empty app list is what they see after the button. They stay signed in.
- Closing a chat tab still writes that chat id into `closedChatIds`. Coming back does not reopen it.
- Closing the browser tab does not write the open chats into `closedChatIds`, does not call Clerk `signOut`, and does not clear `localStorage` or cookies.
- Sign-in is the screen for a session Clerk reports as `signed-out`. A loading session and a present cookie are not that screen.
- **Go to your apps** is at least 44×44 points on a touch screen. The card text uses `aria-live="polite"`.

## Technical Design

### Architecture

Two changes. The download helper stays as it is.

The bridge return adopts the iPad's newest `chat-tab-session-v2:` session onto the new window id before prune. A pure helper decides the flags so the rule can be tested without Electron:

- The bootstrap sender id is `WEB_BRIDGE_SENDER_ID`. `adoptPriorSession` is true. `restorableWindowSessionIds` is the Electron product-window ids plus this new bridge window id.
- Any other sender keeps today's rule. `adoptPriorSession` is `mayMigrateLegacyChatTabSession` (true only for the first product window). `restorableWindowSessionIds` stays the product-window ids.

`src/renderer.tsx` already promotes when the flag is true, then prunes. Promote copies `tabs`, `selectedTabInstanceId`, and `closedChatIds`, and it no-ops when the target key already has a session. After the copy, prune deletes keys whose window ids are not restorable. The new bridge id is restorable, so the copy survives and the previous bridge key is removed. A second Electron window still does not adopt, and prune still drops sessions for Electron windows that are gone.

The chat route stops treating URL ids as selected until one `ipc.chat.getChat(chatId)` succeeds. That call already runs both guards, because `assertChatVisible` calls `assertAppVisible`. The ids to confirm are the adopted open tabs, with the URL id included when it is one of them. Success selects the chat and the app from the row. An id that throws `Chat not found` or `App not found` is removed from the open set for this load. The selected tab becomes the next adopted open tab that resolves. When none resolve, clear both atoms, replace the route with `/` only after they tap **Go to your apps**, and show the one card until then. Any other error stays a real error and does not send the person home.

Login is the Clerk cookie already on this origin. `ClerkSessionBridge` republishes the token after load. Nothing on socket close, `pagehide`, or unload calls `signOut` or clears site data. `RequireSignedIn` keeps redirecting only for `signed-out`, and it keeps putting the current path in `redirect`. This change does not set a session-only cookie.

### Components Affected

- `src/window_infrastructure/chat_tab_session_restore.ts` — new pure helper for `adoptPriorSession` and `restorableWindowSessionIds`.
- `src/ipc/handlers/window_infrastructure_handlers.ts` — bootstrap uses that helper. The bridge sender adopts. A later Electron window does not.
- `src/pages/chatMissingRoute.ts` — new. `isMissingChatOrAppError` is true only for the messages `Chat not found` and `App not found`.
- `src/pages/chat.tsx` — do not set `selectedChatIdAtom` or `selectedAppIdAtom`, and do not mount `ChatPanel` or `PreviewPanel`, until `getChat` succeeds for a restored open tab. Drop only the ids that miss. Show the one card when every restored id misses. **Go to your apps** navigates to `/` with `replace: true`.
- Locale files under `src/i18n/locales/*/chat.json` — the card sentences, following `rules/i18n.md`.

Unchanged: `src/lib/factoryDocuments.ts`, `src/components/chat/FactoryPhaseBar.tsx`, `src/control_plane/guard.ts`, `src/hooks/useProposal.ts` (`showErrorToast` stays for a live chat), `src/main/browser_bridge.ts`, `src/auth/RequireSignedIn.tsx`, `src/auth/ClerkAuthProvider.tsx`, preview iframe files, Neon, and `postgres`. `promoteMostRecentChatTabSession` and `pruneChatTabWindowSessions` keep their current behavior. The bootstrap flags are what change.

### Data Model Changes

None. `closedChatIds` stays the explicit-close list inside the existing `chat-tab-session-v2` value. Open tabs stay `tabs`. The Clerk cookie stays the session. Sqlite on the `config` volume stays the store for apps, chats, and messages.

### API Changes

None. The bootstrap payload fields stay `mayMigrateLegacyChatTabSession` and `restorableWindowSessionIds`. Their values for the bridge sender change.

## Implementation Plan

### Phase 1: Remember which tabs were closed

- [ ] Add the restore helper. The bridge sender sets `adoptPriorSession` and includes its new window id in `restorableWindowSessionIds`. Any other sender keeps the first-product-window rule.
- [ ] Wire that helper into bootstrap. Leave the renderer order as promote, then prune.
- [ ] Do not call `signOut` and do not clear `localStorage` or cookies from bridge disconnect, `pagehide`, or unload.
- [ ] An adopted session keeps `closedChatIds` closed and keeps the previous open tabs and selected tab.

### Phase 2: Confirm restored ids before painting the chat

- [ ] Add `isMissingChatOrAppError`.
- [ ] In `chat.tsx`, confirm `getChat` for each adopted open id before atoms and panels. Show the existing **Loading chats...** string during that check.
- [ ] Drop an id that throws `Chat not found` or `App not found`. Select the next adopted open id that resolves. That is Flow A.
- [ ] When none resolve, show the one card and stay on it until **Go to your apps**. Stay signed in. That is Flow B. The card does not write a new chat row.
- [ ] Leave every other error on the current error path.

## Testing Strategy

## Open Questions

- None that block the change. A later look at the container log can say whether the Dyad process opened a different sqlite during the two minutes away. Restoring the browser's open-versus-closed memory is required either way. Rows that are in the volume sqlite come back with the open tabs.

## Decision Log

- Opening the delivery document on its own page is fine. A dialog on the chat page would avoid the unload, and it would still leave a closed browser tab unrestored. The tab restore is the change that returns the sign-in and the work. The in-page document viewer is out of this plan.
- A chat tab closed inside Dyad stays closed. A browser tab closed by mistake is not that gesture. `closedChatIds` is the record of the first. The Clerk cookie and the newest `chat-tab-session-v2` value are the record of the second.
- The person should not sign in again and should not redo the factory run when the rows are still in sqlite. Login stays the Clerk cookie. The work stays the sqlite file on the `config` volume. This change adopts the saved tabs onto the new bridge window id and confirms those ids against that sqlite. That confirmation is Flow A, and it is how they get the chat back.
- Flow B is the screen for a link whose ids are all missing from sqlite. The card is that screen. **Go to your apps** opens `/`, the list of apps this preview still has. A chat that is missing from sqlite is missing from that list. The card does not restore it, and it does not sign the person out.
- `Chat not found` and `App not found` stay the guard errors. The renderer stops selecting those ids and stops toasting them while it is confirming a restored tab.
- A second Electron product window still does not take another window's tabs. Only the bridge sender gains adoption.
- The white Implementation pane stays a follow-up. The parent chrome was up and the version list could see `Index.tsx`, so the app row existed. That is a different defect from a missing chat id.
- Neon and the Postgres driver stay out. The container sqlite on the compose volume remains the store. `src/main/browser_bridge.ts` stays as it is. `src/lib/factoryDocuments.ts` stays as it is.
