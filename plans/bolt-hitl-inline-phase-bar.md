# Bolt HITL stays on the phase bar

> Generated by swarm planning session on 2026-10-11

## Summary

Bolt’s human-in-the-loop wait currently opens a full-screen dialog over the chat. Move that wait onto the phase bar Bolt already has. The chat, the composer, and the preview stay visible. The phase-move button stays disabled, and the server refuses the move, until every open question for the current phase has been answered by the role it names.

Dyad is the interaction reference only. This plan does not change Dyad, VibeSDK, or Forma.

## Problem Statement

The Project Manager and the Developer share one Bolt walkthrough. They need to read the chat and look at the preview before they let the phase move. Today that decision is a Radix dialog, `SharedGateDialog`, mounted above the chat with a full-screen dimmer and no close button. The dialog covers the transcript.

The same dialog is also an incomplete gate. The deploy patch hides the phase bar’s own move button and deletes the inline question list. The dialog then draws only the Implementation review (`review-approve-dev`, “Approve the Implementation review.”). A Discovery question such as `plan-approve` never appears, so the Project Manager can be blocked in the database and still see a move action. The dialog is titled “Implementation review”, “Move to Implementation”, “Move to Delivery”, or “Approve delivery” depending on state.

## Scope

### In Scope (MVP)

- Remove `SharedGateDialog` from the walkthrough layout, including the dimmer.
- Keep the Discovery, Implementation, and Delivery tabs as the phase indicator. The pressed tab follows the server phase. Tab clicks stay disabled.
- Put the move control back on the right of Bolt’s `FactoryPhaseBar`, with Bolt’s existing labels: “Move to Implementation”, “Move to Delivery”, and “Approve delivery”.
- Show one card per question for the current phase, under that bar and above the transcript.
- Disable the move control while any current-phase question is open. `POST /api/project` with `command: 'transition'` returns 403 in that same case.
- The targeted role sees the question body and the answer field. The other role sees “Waiting on the Project Manager.” or “Waiting on the Developer.” and does not receive the body.
- Show the move button only to the role who is allowed to move this phase. While a question they can answer is still open, the button is disabled and the line next to it says “Answer this question to continue.”
- Keep phase changes and answers on `POST /api/project`. Widen `command: 'answer'` so any current-phase question can be answered by its target role. Insert a developer chat message only for the Implementation review, and only on the first successful answer.
- Leave Download on the delivered bar. Leave the composer send rule as it is.
- Update the walkthrough unit tests and the Playwright specs that currently require the dialog.

### Out of Scope (Follow-up)

- Any edit to Dyad, VibeSDK, or Forma.
- Porting Dyad’s `FactoryPhaseBar`, phase-shade chips, or `HitlQuestionList`.
- Dyad’s button text (“Approve and continue to Implementation”). Bolt keeps “Move to …”.
- Dyad’s choice to leave the approve button enabled while a question is open. Bolt blocks. That difference is intentional.
- Clickable phase tabs.
- A new HITL route, a notification, or a history of questions from earlier phases.
- Showing the saved answer text on the card. The card shows “Answered by {name}.”
- Clerk sign-in, Wewebplus role assignment, and the shared project tables.
- A new composer lock.

## User Stories

- As the Project Manager in Discovery, I want “Move to Implementation” on the phase bar, with the chat still visible, so I can read the plan and then move the work.
- As the Project Manager, I want an open `plan-approve` card under the bar, and I want that button disabled until I answer, so I cannot skip the question.
- As the Developer during that question, I want “Waiting on the Project Manager.” and no question text, so I know who is holding the phase.
- As the Developer in Implementation, I want the review card and a disabled “Move to Delivery” until I answer, beside the files and the preview.
- As the Project Manager during that review, I want “Waiting on the Developer.” and no answer field.
- As the Developer, after my review is stored, I want “Move to Delivery” to enable, and I want a second submit to leave the first answer unchanged.
- As the Project Manager in Delivery, I want “Approve delivery” on the bar. The Developer sees “Waiting on the Project Manager.” and no approve button.
- As either role, I want the transcript and the preview on screen through Delivered, and I want Download with no dialog once the project is delivered.

## UX Design

### User Flow

The phase bar is the first block in the chat column, under the chat header. Question cards sit under the bar. The transcript and the composer stay in normal flow. Nothing is fixed, modal, or inert.

1. The person opens the walkthrough. The left side shows Discovery, Implementation, and Delivery. The current phase is pressed. Later tabs stay disabled.
2. The right side shows the move control only when this role may move the current phase.
3. A question arrives for this phase. The control stays visible and becomes disabled. One card appears per open question.
4. The matching role reads the question, types an answer, and chooses Submit answer. The other role sees only who the question is waiting on.
5. When every current-phase question is answered, the waiting line goes away and the move control enables for the role who may transition.
6. That person chooses the control. Bolt’s existing transition runs, including the builder kickoff for the next phase. There is no confirm dialog.

### Key States

- **Clear phase**: No question cards. The move control is enabled for the role who may transition. No waiting line.
- **Open question, matching role**: The move control is disabled. The line says “Answer this question to continue.” The card shows the question body, an answer field, and Submit answer.
- **Open question, other role**: No move control. The line says “Waiting on the Project Manager.” or “Waiting on the Developer.” The card repeats that sentence. The body is not in the DOM.
- **Blocked on the other role, but this role may still move later**: The move control stays visible and disabled. The line names the role that still owes an answer, using the same “Waiting on the …” sentence.
- **Answered**: The field is gone. The card shows “Answered by {name}.” The question body stays for the role who was allowed to see it.
- **Several questions**: One card each. The move stays disabled until every question on this phase is answered, including a question this person cannot answer.
- **Submit in progress**: The field and Submit answer are disabled. The typed text stays.
- **Submit failed**: The typed answer remains. The card shows “Couldn't save the answer. Try again.” No dialog.
- **Delivered**: No cards and no move control. The Download button remains.

### Interaction Details

Column order: chat header, phase tabs and move control, waiting line, question cards, the existing phase hint and comments, transcript, composer.

The move control is one button:

| Phase | Label | Who sees it |
| --- | --- | --- |
| Discovery | Move to Implementation | Project Manager |
| Implementation | Move to Delivery | Developer |
| Delivery | Approve delivery | Project Manager |

Disabled uses the real `disabled` attribute. Do not add a lock icon on this button, and do not restyle it into Dyad’s shaded phase chips.

The waiting line is visible text, not a tooltip. Do not put step ids (`plan-approve`, `review-approve-dev`) in that sentence.

The question body wraps. Submit answer is disabled when the trimmed value is empty. Whitespace-only is empty. An empty submit does not call the server.

The other role’s card does not include the body in a tooltip or an accessible name.

No dialog, no dimmer, no “Implementation review” popup, no focus trap, and no scroll lock.

### Accessibility

- The bar is a region named “Project phases”. The current phase button has `aria-pressed="true"`.
- The move button’s accessible name is its visible label. While the waiting line is showing, `aria-describedby` points at that line.
- The waiting line is `aria-live="polite"`.
- The answer field’s accessible name is “Answer {step id}”, matching the card Bolt already generates. The empty submit control is disabled.
- A save error is text in the card, not a toast.
- The waiting line uses Bolt’s secondary text color. The disabled state and the sentence carry the same message, so color is not the only signal.

## Technical Design

### Architecture

Bolt’s UI is not in this checkout. Deploy checks out `Awannaphasch2016/bolt.diy` at `cursor/website-walkthrough-55d6` and patches it from `scripts/doppler/bolt-workflow.mjs` and `scripts/doppler/bolt-hitl.mjs` on `cursor/hitl-visibility-beside-walk-fd29`.

The implementation branch stacks on that visibility branch, not on `main`. `main` does not contain the Bolt walk.

Keep a single snapshot. The bar reads `sharedSnapshot` from `GET /api/project`, which already polls about every 2 seconds. Do not remount `HitlGateList`. That list polls `GET /api/hitl` on its own, and `applyBoltWorkflowPatches` deletes it today. Two polls would drift. The card markup and the `hitl-*` ids from that list move onto the phase bar, fed by the project snapshot.

`canTransition` keeps its current meaning: this role is the one who may move the current phase. It stays true while a question is open, so the button can be shown disabled. A separate check, any current-phase question with `status === 'open'`, disables the button and makes `command: 'transition'` return 403. The 403 body is “Answer the open question before moving this phase.” It does not include the question text.

`patchSharedBaseChat` stops inserting `SharedGateDialog` and strips a leftover import. `gateDialogSource` is no longer written. `patchSharedPhaseBar` stops wrapping the approve control in `{false && …}`. It keeps phase tabs as a bare `disabled`, keeps Download, and renders the move control, the waiting line, and the cards.

The transition click still posts `{ command: 'transition' }`, stores the returned snapshot, and runs the existing `kickoffFor` plus `startBuilderTurn`. That kickoff is what starts the Implementation builder turn.

### API Changes

| Call | Change |
| --- | --- |
| `GET /api/project` | `questions` lists every question whose phase is the current project phase. `body` is null unless `roleId` matches `targetRoleId`. `canAnswer` is that match and `status === 'open'`. `canTransition`, `transitionLabel`, and `canDownload` stay. `waitingLabel` considers every open current-phase question, not only the Implementation review. |
| `POST /api/project` `command: 'transition'` | Still the phase change, the Implementation-question insert, and the kickoff snapshot. Returns 403 when any current-phase question is open, including for the role who could otherwise move. A wrong-role transition stays 403 when nothing is open. |
| `POST /api/project` `command: 'answer'` | Accepts a question in the current phase when the caller’s role owns it. The developer chat-message insert stays only for `review-approve-dev`, and only when the open-to-answered update returns a row. A second answer stores nothing new. `plan-approve` updates the question and the answer row only. |
| `POST /api/hitl` and `POST /api/hitl/:id/answers` | Unchanged. |

`handleProject` and the generated `workflowServerSource` both change. They drift if only one is edited.

## Open Questions

None that block the MVP. These stay as recorded decisions:

- The other role does not see a disabled move button. They see the waiting sentence. A button they can never press is a false control.
- The saved answer text is not rendered on the card in this version. “Answered by {name}.” is enough to see that the gate cleared.
- Phase tabs stay non-clickable so one browser cannot show a phase the other browser has not reached.

## Decision Log

- **Bolt only.** Dyad shows how a phase bar can hold the wait without covering the chat. Bolt keeps its own bar, its own “Move to …” labels, and its own accent button.
- **Block on an open question.** Dyad does not disable “Approve and continue” when a question is open. The Bolt requirement is stronger: progression waits for the human answer. The button and `command: 'transition'` both enforce it.
- **One snapshot, not HitlGateList.** Remounting the list would poll a second endpoint and fight the workflow patch that deletes it. The bar paints cards from `GET /api/project`.
- **Answers stay on `command: 'answer'`.** That path already inserts the one developer chat message the walk checks. `POST /api/hitl/:id/answers` stays for direct API checks and does not gain that insert.
- **`canTransition` is the role check.** The open-question check is separate, so the allowed role still sees a disabled button instead of no button.
- **Waiting copy stays.** “Waiting on the Developer.” and “Waiting on the Project Manager.” are the sentences the walk already shows. “Answer this question to continue.” is only for the person who still owes an answer. Step ids stay off both lines.
- **Dialog ids are retired.** `shared-gate*` named the popup. The bar uses `factory-phase-continue` and `hitl-*`.
