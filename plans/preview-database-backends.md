# Preview backends for branching and non-branching databases

> Generated by swarm planning session on 2026-10-08
>
> The interactive planning team tools were not available in this session. The plan records the decisions already made in the preview discussion. Product, UX, and engineering trade-offs below are resolved from that discussion and from `rules/product-principles.md`.

## Summary

Keep one preview lifecycle for every builder: a pull-request label creates an isolated public URL, the URL stays up, and removing the label or closing the pull request deletes that preview. Dyad keeps its Neon branch and Namespace deploy. Vibe SDK gets its own label, its own Worker, and its own empty D1 database. Several previews of the same app can stay up together.

## Problem Statement

People inspecting a pull request need a stable public URL that is isolated from production and from other pull requests. Dyad already has that through the `preview` label: Namespace runs the containers, and Neon creates `preview-pr-<number>` from a sanitized parent. Vibe SDK does not. Its lab is one shared Worker, `vibesdk-lab`, republished by hand at `https://vibesdk-lab.karant-test-egress-canary.workers.dev`. D1 cannot branch, so the Neon strategy cannot be copied onto every builder we try.

## Scope

### In Scope (MVP)

- Leave the existing `preview` label, Namespace devbox, Neon branch names, tunnel hostnames, and compose project unchanged.
- Add a separate label, `preview-cloudflare`, that deploys one Vibe SDK Worker for that pull request.
- Give that preview its own empty D1 database, KV namespace, and R2 bucket, named for the pull request.
- Publish `https://vibesdk-pr-<number>.karant-test-egress-canary.workers.dev` and set `CUSTOM_DOMAIN` to that host.
- Delete that Worker, D1 database, KV namespace, and R2 bucket when the label is removed or the pull request closes.
- Allow more than one Vibe SDK preview at a time. Creating one does not wipe another.
- Share only the label decision (update versus destroy). Keep the Namespace jobs and the Cloudflare jobs in separate workflows.
- Keep `vibesdk-lab` as the long-lived walkthrough. Do not reuse its database, KV, R2, or Worker name for a pull request.

### Out of Scope (Follow-up)

- A public URL for an app generated inside Vibe SDK. This account cannot use Workers for Platforms, and the lab build omits the sandbox container.
- Dump and restore of preview data.
- One shared database that is wiped when the active preview changes.
- Postgres schemas inside one server.
- Bolt and Forma deploy jobs. They can declare `branch` or `database` later. This MVP does not deploy them.
- Changing Dyad's Neon parent, Clerk origins, or `pr-<number>.anakwannaphaschaiyong.com`.
- Production Worker `vibesdk-production`, production D1, production KV, production R2, or `build.cloudflare.dev`.
- Replacing the manual lab workflow.

## User Stories

- As a reviewer, I want the existing `preview` label to keep opening Dyad at `https://pr-<number>.anakwannaphaschaiyong.com` so that current inspections do not move.
- As a reviewer, I want `preview-cloudflare` on a pull request to open a Vibe SDK builder that only that pull request uses.
- As a reviewer, I want two labeled Vibe SDK pull requests to stay up at the same time so I can compare them.
- As a reviewer, I want removing the label, or closing the pull request, to remove that preview's URL and its database.
- As a reviewer, I want a new Vibe SDK preview to start from an empty migrated database so another pull request's schema and rows cannot leak in.

## UX Design

### User Flow

1. The reviewer adds `preview` or `preview-cloudflare` to a pull request in this repository. The two labels are independent. A pull request may have one, both, or neither.
2. The matching workflow comments on the pull request with "Provisioning" and the URL it will use.
3. When the deploy is healthy, the comment becomes the live URL. Dyad stays on `https://pr-<number>.anakwannaphaschaiyong.com`. Vibe SDK is `https://vibesdk-pr-<number>.karant-test-egress-canary.workers.dev`.
4. The URL keeps serving until that label is removed or the pull request closes. A second preview does not replace the first.
5. Removal comments that the URL and its database, KV, and R2 bucket were deleted.

### Key States

- **Default**: The label is present and the last deploy succeeded. The comment shows the URL.
- **Loading**: The label was just added or the branch moved. The comment says the preview is provisioning and keeps the previous URL if one is still serving.
- **Empty**: The Vibe SDK database has the app schema and no users or chats. The reviewer signs up on that URL.
- **Error**: Provisioning failed. The comment says the preview was not updated. An older successful preview for that same pull request stays up. No other pull request's database is touched.

### Interaction Details

The only new control is the `preview-cloudflare` label. Reviewers do not pick a database mode. The app declaration does that. The GitHub comment is the status surface, same as finding the URL from the existing preview run.

### Accessibility

The status is a pull-request comment with the full URL as text, so it is available without the GitHub checks UI.

### Consistency notes

`preview` continues to mean Dyad on Namespace. `preview-cloudflare` means Vibe SDK on Cloudflare. The words in front of the reviewer stay "add a label, open the URL, remove the label."

## Technical Design

### Architecture

Two workflows share one pure decision function and nothing else.

`commandForPullRequest` in `deploy/preview/transition.mjs` today returns `update` or `destroy` for the single label `preview`. Generalize that decision so a caller passes the label name. Closing the pull request destroys every preview label that was present. Removing one label destroys only that backend. Adding `preview` to a closed pull request still skips, matching today's rule. A synchronize event with neither label still does not destroy.

`.github/workflows/preview.yml` keeps calling that function for `preview` and keeps the Namespace, Neon, tunnel, and Clerk jobs. Those jobs are not edited to know about D1 or Wrangler.

A new workflow, triggered by the same pull-request event types, calls the function for `preview-cloudflare`. Its deploy job creates or updates only that pull request's Cloudflare resources. Its destroy job deletes only those resources.

Each app declares one database operation:

- `branch` — Dyad. `ensurePreviewBranch` / `deletePreviewBranch` in `deploy/preview/neon.mjs`. The branch name remains `preview-pr-<number>`. The parent must stay a sanitized Neon branch. `br-mute-shadow-b3jxqoho` stays refused.
- `database` — Vibe SDK. Create an empty D1 database, apply the migrations from that pull request's Vibe SDK checkout, and bind that database id only to that Worker. Delete the database on destroy.

D1 has no copy-on-write branch. Time Travel restores one database in place and cannot fork a second copy. Workers Paid allows 50,000 D1 databases on the published limit, billed by queries and storage. An empty preview database is the isolation boundary.

The Worker name is `vibesdk-pr-<number>`. The workers.dev hostname is that name plus `karant-test-egress-canary.workers.dev`. `CUSTOM_DOMAIN` must equal that full host. KV and R2 follow the same pull-request name and are deleted with the Worker.

Resource creation refuses these production and lab identities: Worker `vibesdk-production`, D1 `c4721a2b-b96a-428a-8b2a-b3d255b307e9`, KV `f066f3c2e4824981b48e8586c04db9c1`, R2 `vibesdk-templates`, route `build.cloudflare.dev`, Worker `vibesdk-lab`, and D1 name `vibesdk-lab`.

Fork pull requests stay excluded, same as `preview.yml`.

### Components Affected

- `deploy/preview/transition.mjs` — accept a label name. Preserve today's results when the name is `preview`.
- `deploy/preview/transition.test.mjs` — both labels, including "close destroys both" and "unlabel destroys one".
- `.github/workflows/preview-cloudflare.yml` — new workflow. `preview.yml` is not given Wrangler steps.
- A new D1 preview module next to `deploy/preview/neon.mjs` — create, migrate, delete, and refuse lab and production ids.
- The existing Vibe SDK lab deploy script remains the manual walkthrough. The pull-request workflow may call the same resource helpers only if those helpers refuse the lab and production names.

### Data Model Changes

No Dyad schema change. Each Vibe SDK preview gets a new D1 database whose only schema is that checkout's migrations applied to an empty database. Preview rows live only in that database. They are not copied to `vibesdk-lab` or to Neon.

### API Changes

No public Dyad API. The Cloudflare preview uses the existing D1, KV, R2, and Worker APIs with pull-request names. The pull-request comment is the user-facing status.

## Implementation Plan

### Phase 1: Decision function only

- [ ] Parameterize the label name in `commandForPullRequest` without changing results for `preview`.
- [ ] Add tests: `preview-cloudflare` updates and destroys on its own; closing the pull request destroys both; a push without either label destroys nothing; adding a label to a closed pull request skips.

### Phase 2: One Cloudflare preview

- [ ] On `preview-cloudflare`, create `vibesdk-pr-<number>`, an empty D1 database, a KV namespace, and an R2 bucket.
- [ ] Apply that checkout's Vibe SDK migrations to the new D1 database only.
- [ ] Deploy the Worker with `CUSTOM_DOMAIN` set to `vibesdk-pr-<number>.karant-test-egress-canary.workers.dev`.
- [ ] Comment the URL on the pull request after health succeeds.
- [ ] On unlabel or close, delete that Worker, D1 database, KV namespace, and R2 bucket, then comment that the URL is gone.
- [ ] Refuse lab and production resource ids before any create or delete.

### Phase 3: Leave room for the next builder

- [ ] Document the `branch` and `database` operations in this plan's module boundary. Do not add Bolt or Forma deploy jobs until one of those apps is actually being previewed.

## Risks & Mitigations

| Risk | Likelihood | Impact | Mitigation |
| --- | --- | --- | --- |
| A Cloudflare job is added inside `preview.yml` and a bad edit takes down Dyad previews | Medium | High | New workflow file. `preview.yml` stays on the `preview` label only. |
| A preview migrates `vibesdk-lab` or the production D1 database | Low | High | Refuse those names and ids before create, migrate, or delete. |
| Label removal fails partway and leaves a database behind | Medium | Medium | Delete is keyed by the pull-request name and is safe to rerun. The destroy job logs which resources remain. |
| Two deploys of the same pull request race | Medium | Medium | One concurrency group per pull request and backend. |
| Reviewers expect the generated bakery app to have its own public URL | High | Medium | State in the pull-request comment that this preview is the builder. Generated-app preview stays out of scope. |
| The admin Doppler token ends up on the Namespace workflow | Low | High | Cloudflare secrets stay on the Cloudflare workflow. The Namespace workflow keeps its current OIDC fetch. |

## Open Questions

- Whether the first Cloudflare preview should comment on the pull request or only print the URL in the Actions log. The plan chooses a comment so reviewers do not have to open the log. Implementation can start with the log if comment permissions are awkward, and add the comment in the same phase.
- Which Doppler identity the Cloudflare workflow uses. It must not be wired into `preview.yml`. The lab's admin token is a last resort for that new workflow only.

## Decision Log

- The shared contract is the label lifecycle, not one workflow body. Namespace and Cloudflare deploys stay separate.
- `preview` remains Dyad on Namespace. Vibe SDK uses `preview-cloudflare`, so an existing Dyad review cannot accidentally publish a Worker.
- Non-branching databases get a new empty database per preview, not one wiped slot. Multiple previews stay up together.
- D1 cannot branch. Time Travel is not a substitute. Schema and inspection data live in that preview's database until the label is removed.
- Neon branching for Dyad stays `preview-pr-<number>` from a sanitized parent.
- KV and R2 are isolated per preview the same way, because they also cannot branch.
- `vibesdk-lab` remains the manual walkthrough and is not a pull-request slot.
- Generated-app hosting inside Vibe SDK is deferred. The account cannot use Workers for Platforms.
- Bolt and Forma are not deployed by this MVP. They plug in later by declaring `branch` or `database`.
