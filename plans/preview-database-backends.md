# Preview labels per app

> Generated by swarm planning session on 2026-10-08. Revised the same day: the label names the app, not the infrastructure vendor.
>
> The interactive planning team tools were not available in this session. The plan records the decisions already made in the preview discussion. Product, UX, and engineering trade-offs below are resolved from that discussion and from `rules/product-principles.md`.

## Summary

One preview lifecycle covers every builder. A pull-request label creates an isolated public URL, the URL stays up, and removing that label or closing the pull request deletes that preview. The label names the app. Dyad, Vibe SDK, and Bolt each have their own label, their own workflow, and their own database. Bolt can run on Cloudflare without sharing Vibe SDK's D1 database, KV, R2, Worker names, or secrets. Several previews of the same app can stay up together.

## Problem Statement

People inspecting a pull request need a stable public URL that is isolated from production and from other pull requests. Dyad already has that through the `preview` label: Namespace runs the containers, and Neon creates `preview-pr-<number>` from a sanitized parent. Vibe SDK does not. Its lab is one shared Worker, `vibesdk-lab`, republished by hand at `https://vibesdk-lab.karant-test-egress-canary.workers.dev`. D1 cannot branch, so the Neon strategy cannot be copied onto every builder.

A shared Cloudflare label would also be the wrong grouping. Bolt uses Cloudflare too, and it does not share Vibe SDK's database vendor or the rest of that stack. The thing a reviewer turns on is the app they want to inspect.

## Scope

### In Scope (MVP)

- Keep the existing `preview` label working as Dyad. Same Namespace devbox, Neon branch names, tunnel hostnames, and compose project.
- Treat `preview-dyad` as the same Dyad preview. Either label deploys Dyad. Removing one while the other remains does not destroy it.
- Add `preview-vibesdk`. It deploys one Vibe SDK Worker for that pull request, with its own empty D1 database, KV namespace, and R2 bucket.
- Publish `https://vibesdk-pr-<number>.karant-test-egress-canary.workers.dev` and set `CUSTOM_DOMAIN` to that host.
- Add `preview-bolt` as Bolt's label. Bolt's workflow provisions only Bolt's resources. It does not create a D1 database, a Neon branch, a Vibe SDK Worker, or Dyad containers.
- Delete only the resources owned by the label that was removed. Closing the pull request deletes every app preview that pull request had.
- Allow more than one preview of the same app at a time. Creating one does not wipe another.
- Share only the label decision (update versus destroy). Each app has its own workflow.
- Keep `vibesdk-lab` as the long-lived walkthrough. Do not reuse its database, KV, R2, or Worker name for a pull request.

### Out of Scope (Follow-up)

- Bolt's database vendor and Bolt's public hostname. The label and the isolation rule are in scope. The Bolt deploy job waits until that vendor is named.
- A public URL for an app generated inside Vibe SDK. This account cannot use Workers for Platforms, and the lab build omits the sandbox container.
- Dump and restore of preview data.
- One shared database that is wiped when the active preview changes.
- Postgres schemas inside one server.
- A Forma deploy. `preview-forma` can follow the same label rule later.
- Changing Dyad's Neon parent, Clerk origins, or `pr-<number>.anakwannaphaschaiyong.com`.
- Production Worker `vibesdk-production`, production D1, production KV, production R2, or `build.cloudflare.dev`.
- Replacing the manual lab workflow.
- A `preview-cloudflare` label. Cloudflare is not an app.

## User Stories

- As a reviewer, I want the existing `preview` label to keep opening Dyad at `https://pr-<number>.anakwannaphaschaiyong.com` so that current inspections do not move.
- As a reviewer, I want `preview-dyad` to open that same Dyad preview, so the label name matches the other apps.
- As a reviewer, I want `preview-vibesdk` to open a Vibe SDK builder that only that pull request uses.
- As a reviewer, I want `preview-bolt` to open Bolt on its own URL and its own database, even though Bolt also runs on Cloudflare.
- As a reviewer, I want two labeled Vibe SDK pull requests to stay up at the same time so I can compare them.
- As a reviewer, I want removing one app's label to leave the other apps on that pull request alone.

## UX Design

### User Flow

1. The reviewer adds one app label to a pull request in this repository: `preview` or `preview-dyad`, `preview-vibesdk`, or `preview-bolt`. The labels are independent. A pull request may carry more than one.
2. That app's workflow comments on the pull request with "Provisioning" and the URL it will use. The comment names the app.
3. When the deploy is healthy, the comment becomes the live URL. Dyad stays on `https://pr-<number>.anakwannaphaschaiyong.com`. Vibe SDK is `https://vibesdk-pr-<number>.karant-test-egress-canary.workers.dev`. Bolt's hostname is chosen with Bolt's deploy, not borrowed from Vibe SDK.
4. The URL keeps serving until that app's label is removed or the pull request closes. A second preview does not replace the first.
5. Removal comments that this app's URL and its own database were deleted. Another app's preview on the same pull request stays up.

### Key States

- **Default**: The label is present and the last deploy succeeded. The comment shows the app name and the URL.
- **Loading**: The label was just added or the branch moved. The comment says that app's preview is provisioning and keeps the previous URL if one is still serving.
- **Empty**: A Vibe SDK database has that checkout's schema and no users or chats. The reviewer signs up on that URL. Bolt starts empty in Bolt's own database.
- **Error**: Provisioning failed. The comment says that app's preview was not updated. An older successful preview for that same app and pull request stays up. No other app's database is touched.

### Interaction Details

Reviewers pick an app label. They do not pick a cloud vendor or a database mode. The app's workflow owns both. The GitHub comment is the status surface.

### Accessibility

The status is a pull-request comment with the app name and the full URL as text, so it is available without the GitHub checks UI.

### Consistency notes

`preview` and `preview-dyad` mean Dyad. `preview-vibesdk` means Vibe SDK. `preview-bolt` means Bolt. The words in front of the reviewer stay "add the app's label, open the URL, remove the label."

## Technical Design

### Architecture

Each app is a preview target. The targets do not share resource names.

| Label | App | Where it runs | Database | URL |
| --- | --- | --- | --- | --- |
| `preview`, `preview-dyad` | Dyad | Namespace devbox `Wewebplus-ci` | Neon branch `preview-pr-<number>` | `https://pr-<number>.anakwannaphaschaiyong.com` |
| `preview-vibesdk` | Vibe SDK | Its own Worker | Its own empty D1 database | `https://vibesdk-pr-<number>.karant-test-egress-canary.workers.dev` |
| `preview-bolt` | Bolt | Bolt's own Cloudflare deploy | Bolt's own database vendor, chosen by Bolt | Chosen with Bolt's deploy |

`commandForPullRequest` in `deploy/preview/transition.mjs` today returns `update` or `destroy` for the single label `preview`. Generalize that decision so a caller passes the label name. `preview` and `preview-dyad` are one Dyad target: the preview is destroyed only when both are absent, or when the pull request closes. Removing `preview-vibesdk` destroys only Vibe SDK. Removing `preview-bolt` destroys only Bolt. Adding a label to a closed pull request still skips. A synchronize event with no preview label still does not destroy.

`.github/workflows/preview.yml` keeps the Namespace, Neon, tunnel, and Clerk jobs. Those jobs are not edited to know about D1, Wrangler, or Bolt.

`.github/workflows/preview-vibesdk.yml` calls the decision function for `preview-vibesdk`. It creates and deletes only `vibesdk-pr-<number>` and that preview's D1, KV, and R2.

`.github/workflows/preview-bolt.yml` calls the decision function for `preview-bolt`. Its jobs create and delete only Bolt resources. They do not call the Vibe SDK helpers or the Neon helpers.

Each app declares its own database operation inside its workflow:

- Dyad uses `branch`. `ensurePreviewBranch` / `deletePreviewBranch` in `deploy/preview/neon.mjs`. The branch name remains `preview-pr-<number>`. The parent must stay a sanitized Neon branch. `br-mute-shadow-b3jxqoho` stays refused.
- Vibe SDK uses a new empty database. Create a D1 database, apply the migrations from that pull request's Vibe SDK checkout, and bind that database id only to that Worker. Delete the database on destroy.
- Bolt declares its own operation when its vendor is known. That operation is not D1 and it is not Dyad's Neon project.

D1 has no copy-on-write branch. Time Travel restores one database in place and cannot fork a second copy. Workers Paid allows 50,000 D1 databases on the published limit, billed by queries and storage. An empty Vibe SDK database is that app's isolation boundary. It is not available to Bolt.

The Vibe SDK Worker name is `vibesdk-pr-<number>`. The workers.dev hostname is that name plus `karant-test-egress-canary.workers.dev`. `CUSTOM_DOMAIN` must equal that full host. Vibe SDK's KV and R2 follow the same pull-request name and are deleted with that Worker. Bolt uses its own script names and its own buckets.

Vibe SDK resource creation refuses these production and lab identities: Worker `vibesdk-production`, D1 `c4721a2b-b96a-428a-8b2a-b3d255b307e9`, KV `f066f3c2e4824981b48e8586c04db9c1`, R2 `vibesdk-templates`, route `build.cloudflare.dev`, Worker `vibesdk-lab`, and D1 name `vibesdk-lab`.

Fork pull requests stay excluded, same as `preview.yml`.

### Components Affected

- `deploy/preview/transition.mjs` — accept a label name. Treat `preview` and `preview-dyad` as one Dyad target. Preserve today's results for a pull request that only has `preview`.
- `deploy/preview/transition.test.mjs` — per-app labels, including "close destroys every app" and "unlabel destroys one app".
- `.github/workflows/preview-vibesdk.yml` — new workflow. `preview.yml` is not given Wrangler steps.
- `.github/workflows/preview-bolt.yml` — new workflow shell that decides update versus destroy. The Bolt provision and delete steps land when Bolt's database vendor is named.
- A new D1 preview module next to `deploy/preview/neon.mjs` — used only by Vibe SDK. Create, migrate, delete, and refuse lab and production ids.
- The existing Vibe SDK lab deploy script remains the manual walkthrough. The pull-request workflow may call the same resource helpers only if those helpers refuse the lab and production names.

### Data Model Changes

No Dyad schema change. Each Vibe SDK preview gets a new D1 database whose only schema is that checkout's migrations applied to an empty database. Those rows are not copied to `vibesdk-lab`, to Neon, or to Bolt. Bolt's rows stay in Bolt's database.

### API Changes

No public Dyad API. Vibe SDK's preview uses D1, KV, R2, and Worker APIs with Vibe SDK pull-request names. Bolt uses its own APIs. The pull-request comment is the user-facing status.

## Implementation Plan

### Phase 1: Decision function only

- [ ] Parameterize the label name in `commandForPullRequest` without changing results for a pull request that only has `preview`.
- [ ] Treat `preview` and `preview-dyad` as one Dyad target.
- [ ] Add tests: `preview-vibesdk` and `preview-bolt` update and destroy on their own. Closing the pull request destroys every app preview. A push with no preview label destroys nothing. Adding a label to a closed pull request skips.

### Phase 2: Vibe SDK preview

- [ ] On `preview-vibesdk`, create `vibesdk-pr-<number>`, an empty D1 database, a KV namespace, and an R2 bucket.
- [ ] Apply that checkout's Vibe SDK migrations to the new D1 database only.
- [ ] Deploy the Worker with `CUSTOM_DOMAIN` set to `vibesdk-pr-<number>.karant-test-egress-canary.workers.dev`.
- [ ] Comment the URL on the pull request after health succeeds.
- [ ] On unlabel or close, delete that Worker, D1 database, KV namespace, and R2 bucket, then comment that the URL is gone.
- [ ] Refuse lab and production resource ids before any create or delete.

### Phase 3: Bolt's own resources

- [ ] Add the `preview-bolt` workflow so the label is recognized.
- [ ] When Bolt's database vendor is named, provision and delete only that vendor's preview resources. Do not call the D1 module or the Neon module from Bolt's workflow.

## Testing Strategy

- [ ] Unit tests for the label decision, including Dyad plus Vibe SDK on one pull request, and Vibe SDK plus Bolt on one pull request.
- [ ] Unit tests that a Vibe SDK D1 name cannot be `vibesdk-lab`, `vibesdk-production`, or a production database id, and that Bolt's workflow does not reference those helpers.
- [ ] A preview run on a disposable pull request: two `preview-vibesdk` labels on two pull requests, both URLs healthy, signup on one absent from the other.
- [ ] Remove `preview-vibesdk` from a pull request that also has `preview` and confirm Dyad's URL still serves and only the Vibe SDK Worker and D1 database are gone.
- [ ] Add `preview` to a pull request and confirm the URL is still `https://pr-<number>.anakwannaphaschaiyong.com` and that no `vibesdk-pr-<number>` Worker was created.

## Risks & Mitigations

| Risk | Likelihood | Impact | Mitigation |
| --- | --- | --- | --- |
| A Vibe SDK or Bolt job is added inside `preview.yml` and a bad edit takes down Dyad previews | Medium | High | One workflow file per app. `preview.yml` stays on Dyad. |
| Vibe SDK and Bolt share a database because both use Cloudflare | Medium | High | Labels and workflows are per app. Bolt does not call the D1 module. |
| A Vibe SDK preview migrates `vibesdk-lab` or the production D1 database | Low | High | Refuse those names and ids before create, migrate, or delete. |
| Label removal fails partway and leaves a database behind | Medium | Medium | Delete is keyed by the app and the pull-request number and is safe to rerun. |
| Two deploys of the same app and pull request race | Medium | Medium | One concurrency group per app and pull request. |
| Reviewers expect the generated bakery app to have its own public URL | High | Medium | The Vibe SDK comment says this preview is the builder. Generated-app preview stays out of scope. |
| Renaming `preview` to `preview-dyad` strands current reviews | Medium | High | `preview` keeps deploying Dyad. `preview-dyad` is an additional name for the same target. |
| The admin Doppler token ends up on the Dyad or Bolt workflow | Low | High | Each workflow fetches only the secrets that app uses. |

## Open Questions

- Bolt's database vendor and hostname. The label is decided. The provision steps wait for that choice.
- Whether the first Vibe SDK preview should comment on the pull request or only print the URL in the Actions log. The plan chooses a comment so reviewers do not have to open the log.
- Which Doppler identity the Vibe SDK workflow uses. It must not be wired into `preview.yml` or the Bolt workflow. The lab's admin token is a last resort for the Vibe SDK workflow only.

## Decision Log

- The label names the app. `preview` and `preview-dyad` are Dyad. `preview-vibesdk` is Vibe SDK. `preview-bolt` is Bolt. There is no Cloudflare label.
- Bolt uses Cloudflare and still gets its own database vendor, resource names, secrets, and workflow.
- The shared contract is the label lifecycle, not one workflow body and not one cloud account's databases.
- `preview` keeps today's Dyad behavior so existing reviews do not move.
- Non-branching databases get a new empty database per preview, not one wiped slot. Multiple previews stay up together.
- D1 cannot branch. Time Travel is not a substitute. Vibe SDK schema and inspection data live in that preview's D1 database until `preview-vibesdk` is removed.
- Neon branching for Dyad stays `preview-pr-<number>` from a sanitized parent.
- Vibe SDK's KV and R2 are isolated per preview because they also cannot branch. They are not Bolt's buckets.
- `vibesdk-lab` remains the manual walkthrough and is not a pull-request slot.
- Generated-app hosting inside Vibe SDK is deferred. The account cannot use Workers for Platforms.
- Bolt's deploy job is deferred until its database vendor is named. The label rule is not deferred.
