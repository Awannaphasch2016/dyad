## Summary

## Problem Statement

Reviewers can open an isolated Dyad preview with the `preview` label. Vibe SDK’s only public address today is the shared lab. The per-pull-request builder is written and unproven. Until someone adds `preview-vibesdk` to a pull request that contains the workflow, there is no URL to open.

## UX Design

### User Flow

1. Pull request 68 is open. Add the label whose name is exactly `preview-vibesdk`.
2. One comment appears: “Vibe SDK preview is provisioning.” There is no URL yet.
3. The same comment is edited to the `workers.dev` URL, plus the note that this preview is the builder and a generated app does not get its own public URL.
4. Open that URL. Create one account. The next screen is the Vibe SDK home. Do not send a prompt.
5. Return to the pull request and remove `preview-vibesdk` only after the deploy job is green.
6. The same comment becomes “Removed Vibe SDK preview” plus that URL.
7. Load the URL again. The home is gone.

### Key States

- **Before**: No preview comment.
- **Provisioning**: “Vibe SDK preview is provisioning.” No URL.
- **Ready**: “Vibe SDK preview:” plus the URL.
- **Removed**: “Removed Vibe SDK preview” plus the URL that was deleted.
- **Deploy failed**: “Vibe SDK preview was not updated.” No URL to open.
- **Cleanup failed**: “Vibe SDK preview cleanup did not finish.” The URL may still open. This is not Removed.

### Interaction Details

The label is the only control. The comment is the only status. GitHub edits that one comment. The full URL is the link. The lab is not linked from the comment.

The label list also contains `preview`. Choosing that label deploys Dyad and does not produce this comment. The provisioning sentence is the sign that `preview-vibesdk` was the label added.

Treat the site as stopped only after the comment says Removed. Until then the home can still load.

### Accessibility

The status is the first sentence of the comment. The address is a normal link whose name is the full URL. The HTML marker stays in an HTML comment. Status does not depend on color.

## Technical Design

### Architecture

GitHub runs `.github/workflows/preview-vibesdk.yml` from the pull request that contains it. Pull request 68 contains that file. `main` does not. Labeling any other pull request does nothing until the file is merged or that pull request’s branch has it.

Adding the label runs `up` for pull request 68. That creates only names `vibesdk-pr-68`, pins Vibe SDK at `9da158d82c597a0e8f4bf033cdccd1053fb6fb15`, and refuses the lab and production ids before create. Secrets come from Doppler OIDC, project `dyad`, config `preview`. There is no admin token and no Neon call.

The deploy job does not print `health=200`. A green job means the in-workflow health check returned 200. Confirm with `GET /api/health` on the preview URL. Do not add a log line unless that GET disagrees with the job.

Deploy and destroy share the lock `vibesdk-preview-pr-68` and do not cancel each other. Removing the label while the deploy is still running queues the delete behind it and can take the URL down before anyone opens it. Wait for a green deploy.

A manual rerun is `workflow_dispatch` on branch `cursor/preview-backend-plan-fd29` with input `68`. Dispatch from `main` cannot see the workflow. A second delete that finds nothing logs `deleted=false` and `comment=silent`.
