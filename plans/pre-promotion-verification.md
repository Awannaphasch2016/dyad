## Summary

`pre` is the canary. This plan proves that canary can serve one question and answer on `https://pre.anakwannaphaschaiyong.com` while `https://anakwannaphaschaiyong.com` stays on `gascity-server`. A pass is the evidence required before a later promotion. The pass does not promote anything.

## Problem Statement

The operator cannot tell a real rehearsal from a set of similarly named resources. Doppler `dyad/canary` points at Neon branch `pre`. Doppler `dyad/prd` points at a different project, `wewebplus-production`. A second Neon branch is also named `prd`. The ECS cluster exists and has no task. Treating any of those as permission to move the apex would put production writers on the wrong database, or would move the apex onto a stack that has never answered a question.

## Scope

### In Scope (MVP)

- One recorded pass/fail run of the canary.
- Bring the canary up only far enough to answer one question: images, one ECS task, Doppler `dyad/canary`, and `https://pre.anakwannaphaschaiyong.com`.
- Prove the question lands in the canary sqlite and in Neon branch `pre`, and is absent from `wewebplus-production`.
- Prove the apex, the EC2 container, and `dyad/prd` are unchanged.
- Fail the run while Vercel can still write Neon through `/api/questions`.

### Out of Scope (Follow-up)

- The promotion itself: stopping `gc` and `weaver-plus`, copying volumes, pointing the task at `dyad/prd`, moving the apex, and the production question on the apex.
- Pointing `dyad/prd` at Neon branch `pre`, or rolling `gascity-server`.
- Deleting Vercel project `dyad`, or changing user-app Vercel deploy.
- Weighted traffic, a second canary, or gRPC.
- Renaming or deleting the `Wewebplus-hitl` branch that is named `prd`.

## UX Design

The checklist is the checker’s text output plus this plan. It is not a new page in the product. The canary window is the existing Dyad UI.

### User Flow

1. The operator reads the full canary URL before starting: `https://pre.anakwannaphaschaiyong.com`.
2. They open that URL, confirm the address bar matches it, and sign in with Clerk on that origin. A production session does not carry over.
3. They submit one answer in the existing HITL row in that window and wait until the row shows answered.
4. They open `https://anakwannaphaschaiyong.com` only to look. They do not focus a field and do not submit.
5. The checker prints an overall pass only when every required gate passed. A failure prints `Gate failed: {name}` and the run stops.

### Key States

- **Not started**: no task is serving the canary hostname. Production is the normal site.
- **Running**: the current gate name is printed. Later gates stay not started.
- **Pass**: every required gate passed. The summary says the canary is ready to promote and that promotion has not been done.
- **Fail**: the summary names the gate. Earlier passes stay visible.
- **Empty**: no HITL question appears on the canary within the run. That is `Gate failed: HITL question on pre`, not an indefinite wait.
- **Error**: Clerk keys or the database URL missing is `Gate failed: Clerk and database configuration`. A sign-in screen that never succeeds is `Gate failed: Clerk sign-in`.

### Interaction Details

The answer is typed only in the existing Dyad question row on the canary. The production hostname gains no banner, modal, or checklist. The preview pane, the terminal, and one-way IPC stay desktop-only. Their absence in the browser is recorded as out of scope, not as a failure.

### Accessibility

Gate status is the words `not started`, `running`, `pass`, and `fail`. A failure line always includes the gate name. The operator does not depend on color.

## Technical Design

### Architecture

Three stacks stay distinct.

| Stack | Identity | Verdict |
| --- | --- | --- |
| ECS canary | Doppler `dyad/canary`, Neon branch `pre` | The only candidate |
| Preview compose | `gc` sleeps; `services/gascity-browser` listens on 8787 | Fail if this is what is running |
| EC2 `gascity-server` | `weaver-plus` on the apex | Must stay up and unchanged |

On ECS, GasCity calls `http://dyad:32100`. `127.0.0.1:32100` is the EC2 host-network address and fails this run if it is the canary supervisor’s target. The host bridge binds `0.0.0.0` only inside the ECS task. The security group does not publish 32100, 6080, or 8373. Dyad `desiredCount` stays 1 because sqlite is local to the task volume. Shared memory is 1024. Volumes are new canary disks, not the live EC2 mounts.

The browser bridge marker is `data-dyad-browser-bridge`. The canary sets `DYAD_BROWSER_BRIDGE_PORT=8373`. cloudflared is a sidecar on the Dyad task. The public page is the canary hostname. The bridge process itself stays on loopback inside the task.

`scripts/gascity/verify_bridge.mjs` requires production apps 3 (`sparkling-platypus-soar`) and 4 (`hopping-quokka-buzz`) on branch `main`. The canary volume does not have those apps yet. Requiring that script during this run is a false failure. The canary bridge gate is the marker, a websocket open on `ws://127.0.0.1:8373/dyad-browser-ipc`, and the answered question. That script becomes meaningful after the later volume copy, which this plan does not do.
