# Reuse Clerk ticket sign-in for the two-role HITL check

> Generated by swarm planning session on 2026-10-11

## Summary

The two-role HITL check already signs a Project Manager and a Developer into separate browsers with a 300-second Clerk sign-in token. This plan reuses that GitHub Actions job. It does not add a new login, it does not put the token in a desktop recording, and it does not point the check at the VibeSDK preview.

## Problem Statement

The multi-tenant checklist needs two people signed in at once, in two browsers, on one Wewebplus project. The Development Clerk instance only offers Google, Microsoft, and ticket sign-in. Password is off. The two human accounts must not be used or changed.

That sign-in problem is already solved for the Bolt walkthrough. What is still easy to get wrong is running a second, weaker job and treating it as the same proof, or trying to finish the check from a desktop agent that cannot hold the Clerk secret or two cookie jars.

## Scope

### In Scope (MVP)

- Treat pull request 91, branch `cursor/automated-hitl-verification-851d`, as the checklist runner.
- Keep `signInAs` in `e2e-walkthrough/tests/walkthrough.ts`: mint one Clerk sign-in token per test user, consume it with the ticket strategy, then let clerk-js refresh the session.
- Keep two Playwright browser contexts, one for `walkthrough-pm+clerk_test@example.com` (Project Manager) and one for `walkthrough-dev+clerk_test@example.com` (Developer).
- Keep the outsider `+clerk_test` user, who is never added to Wewebplus, as the not-found check.
- Bring the plan-approve visibility check from pull request 98 onto that same branch without removing `two-roles.spec.ts`.
- Evidence stays the job's existing video per context, screenshots, trace, and JSON report.

### Out of Scope (Follow-up)

- Computer Use, a live desktop cursor, or any path that pastes a ticket into a page or a URL.
- Minting tokens inside a Cursor cloud VM. `CLERK_SECRET_KEY` stays in the GitHub Actions job, loaded from Doppler `bolt/preview`.
- The VibeSDK preview. It trades a Clerk session for its own cookie and does not render these question cards. Its apps are not `bolt-walkthrough`.
- `scripts/gascity/verify_bridge.mjs`. That script injects a session JWT into the Dyad desktop app. It does not open a browser.
- Production Clerk, password or email-code sign-in, and any edit to the two human accounts.
- Filling `bolt/prd`, the Gas City closer, a second organization, or a Harbor-owned app.
- Resetting the shared Bolt project while a person is mid-walkthrough.

## User Stories

- As the person judging the preview, I run one workflow and get two signed-in browsers without using Google or Microsoft.
- As that person, I can see the Project Manager receive a plan-approve body, and the Developer receive the same question with status only, no body, and a refused answer.
- As that person, I can see an account outside Wewebplus get not-found.
- As the owner of the human accounts, those accounts are not signed in and not modified.
- As a reviewer, I can watch the uploaded videos without a sign-in token or a Clerk secret in the log or the picture.

## UX Design

### User Flow

The viewer is the person watching the uploaded recording. Sign-in finishes before the first frame.

1. Each context consumes its ticket off camera. The address bar does not contain the ticket.
2. The first frame is the Bolt walkthrough, signed in. The account control names the role. The phase strip is visible.
3. On Discovery, the Project Manager sees the question body and the answer field. The Developer sees the waiting card: role and status, no body, no field.
4. The Project Manager submits. Both windows show the card answered and name the Project Manager. The Developer still has no body.
5. On Implementation, the roles swap. The Developer uses the field named "Implementation answer". The Project Manager sees only the waiting card, then the answered card.
6. On Delivery, the Project Manager signs off. Both windows can reach download. Sign-out returns each window to signed out.
7. The outsider context, already signed in, opens the same project and sees not-found.

A Build prompt and an orange Sign in button means the run opened the VibeSDK preview. That is a failed run. The checklist does not continue into Google or Microsoft.

### Key States

- **Default**: Signed-in Bolt project, role name visible, phase strip present.
- **Loading**: "Checking sign-in…" is waiting, not success. One reload is allowed. If the phase strip does not appear, the run stops.
- **Empty**: A phase with no question card yet. Wait, reload that phase once, then fail. Do not type into "Describe the page" as if it were an answer.
- **Error**: Sign in returns to the Sign in control with no message. Caption the artifact "sign-in did not stick" and stop. A submit that does not change the card needs an inline failure on the card; a frozen card with no message is a failed frame.
- **Wrong page**: VibeSDK front page. Stop.
- **Waiting role**: Waiting card only. It is text, not a disabled field.
- **Outsider**: Not-found. No phase strip and no question body.

### Interaction Details

- Window titles in the harness say Project Manager and Developer. Those captions are not product UI.
- The human step is the question card, not the phase's "Approve and continue" button. The recording dwells on the card before and after submit.
- Submit shows a pending state and ignores a second click. The typed text stays until the status changes.
- The proof frame is the settled frame after load. A first paint that shows another role's question body is a defect, not a pass.
- The two contexts never share a profile and never switch accounts through a menu.

### Accessibility

- The answer field's accessible name includes the step, matching "Implementation answer".
- The waiting card is not a button and not focusable.
- Status is the word "open" or "answered", not a color.
- The ticket is never placed in a live input, a document title, or an accessible name.
- After sign-in, focus lands on the account name. Only the role who may answer then moves to the field.

## Technical Design

### Architecture

GitHub Actions remains the only place that can mint a ticket. Doppler `bolt/preview` supplies the Development Clerk secret through the existing masked export. `signInAs` creates a one-time token for a known test user id (`expiresInSeconds: 300`) and the page consumes it with `strategy: "ticket"`. Two `browser.newContext()` calls keep two cookie jars. After the ticket is consumed, clerk-js refreshes the session JWT, so the rest of the walk does not mint another ticket unless a context is thrown away.

Pull request 98's branch is not the runner. That branch drops `two-roles.spec.ts` and the delivered check. Its visibility spec is copied onto the pull request 91 branch. The full walk stays.

### Components Affected

- `e2e-walkthrough/tests/walkthrough.ts` — keep `signInAs`. Do not copy it into a second helper.
- `e2e-walkthrough/tests/two-roles.spec.ts` — keep the walk through Delivery.
- `e2e-walkthrough/tests/zz-p3-role-visibility.spec.ts` — add this file onto the pull request 91 branch.
- `.github/workflows/bolt-walkthrough-verify.yml` on `cursor/automated-hitl-verification-851d` — run the visibility spec in the same job as the two-role walk.
- `scripts/doppler/bolt-test-accounts.mjs` — unchanged. Still refuses human emails and a join that would pass the Wewebplus membership cap.
- `scripts/doppler/bolt-reset-project.mjs` — unchanged. Still resets only `bolt-walkthrough`.
- `scripts/gascity/verify_bridge.mjs` — not used.
- VibeSDK preview patches — not used.

### Data Model Changes

None. The test users, Wewebplus memberships, and `bolt-walkthrough` rows already exist. The visibility spec inserts one `plan-approve` question and deletes it when it finishes, including on failure.

### API Changes

None. The page keeps calling Clerk's ticket sign-in and `GET /api/project` with the session bearer. The visibility spec keeps the existing HITL read and answer calls.

## Decision Log

- **Reuse pull request 91.** Product, design, and engineering agreed the ticket helper and the two-context job are the mechanism. A new login would duplicate it.
- **Computer Use is not the runner.** One desktop profile is one cookie jar. The Clerk secret is not on the agent VM. A ticket on screen would be in the recording. Design accepted the two labeled Playwright videos as the thing a person watches.
- **Pull request 98 is an assertion, not a replacement.** Engineering challenged using that branch as the job, because it drops the Delivery walk. Product's visibility, outsider, and single-answer checks are added beside the existing walk.
- **VibeSDK stays out.** All three roles agreed that preview does not render these cards. Adapting `signInAs` onto its cookie exchange is a separate plan.
- **The Electron bridge script stays out.** `verify_bridge.mjs` proves a desktop IPC token. It does not prove the HITL page.
- **No second organization in this change.** The outsider who is not a member is the cross-tenant check. Wewebplus is already near its membership cap.
